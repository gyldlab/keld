## 1. Goal & non-goals

Define the **one product-run evidence contract** required for `electron-apps-v0`, with draw.io as the first candidate. A product cell is an independently observed action in an actual pinned upstream application running on a particular Keld/Bun/engine/OS stack. It is not an import check, a developer-start log, or a mock of an Electron API. The collector binds an actual Host-owned admitted role generation to the pinned app source, its controlled patch (if any), the execution environment, and the specific observed operation. Only the existing KEL-74 record/scorer can turn a qualified observation into a cell verdict.

The initial cell set is **install, activation, open, edit, save and close-with-unsaved-prompt**. Each has a separate success/negative observable. `install` stays `unknown` until a real, independently identified KEL-141 distribution artifact and installer exist. A `keld dev` staged project is never an installed product. A named physical product manifest may be committed only under X02-T6 with a known denominator, valid product receipts and its own reviewer.

Non-goals:

- No production implementation in this *specification* change, no new KEL-78 security profile, OS containment claim, principal, permission grant, reaper or authority-profile map.
- No second KEL-74 parser, scorer, canonical manifest digest, product-id whitelist, Electron pin, or special draw.io case in framework-generic `keld-compat::evidence`.
- No claims that a child-authored stdout/stderr line, arbitrary local JSON, screenshot alone, or app-authored receipt is Host-origin proof.
- No shipping `keld build` / `keld migrate` implementation, prebuilt installer, first committed corpus, compatible-product percentage, or Electron-median score.
- No change to GH-446 facade Ready/window ownership, GH-588 launch enforcement, or any active runtime/Guardian worktree.
- No assumption that mode 0400 or ownership by the same macOS user makes a receipt unforgeable against an uncontained Legacy Bun role.

| C12 · Trusted Host generation | Collector observes an initial/successor application generation | It accepts a Host-owned principal only after verified policy admission, real Host/Guardian attachment, authenticated link and successful **current/running/reader** installation **at action time**; printed `admitted legacy` text, pre-bind death, stale G1 or foreign principal cannot create a **new** successful cell |
| C13 · Frozen request, fresh effective state | G1 exits and G2 is admitted within one Host session | The Host-origin record binds original verified policy digest and **new** G2 principal and its separately witnessed effective state. A forged G2 state reset against Host-witnessed Legacy or replayed G1 also refuses. A genuinely fresh **no-profile Host session** remains valid Unverified evidence |

| C19 · Citations and pin | Declare a v1 `pass`/`fail` cell | It retains the prescribed Electron v44.4.5 pin and byte-verified committed `doc_citation` snapshot (`gh532`). A purely app-specific observation with no applicable citation stays `unknown`, not invented as an Electron normative claim |
| C20 · Source/architecture truth | Review architecture 04 section 6 and the new spec | No `gitignored fixtures`, nonexistent `--headless --smoke` CLI or assumed completed install path remains; reintroducing one is rejected by a docs negative check |
| C21 · Single owner | Inspect code paths and this spec | Product receipt reader/shape extends the existing `corpus_runs` owner under `corpus_manifest`; no second parser, legacy-state label table, scorer, runtime receipt authority or duplicate host identity owner is introduced |
| C22 · Causal G1/G2 operations | A cross-generation asynchronous app action completes after another generation becomes current | A successful cell requires Host-owned initiating request identity **and** independently observed effect commit/completion tied to the same generation; a delayed G1 result observed during G2 cannot be attributed to G2. An ambiguous spanning operation remains `unknown` or is retested with distinct G2-owned data. Inject a delayed G1 write after G2 binding and require misattribution to fail |
| C23 · Attempt census | Multiple attempts or split runs for one product partition/platform/source/profile exist | Collector gives each physical attempt a stable run identity and retains failures/unknowns, current generation changes and cleanup outcomes. One reviewer-approved, deterministic selected run per declared partition/lane or an explicit all-runs report is published; dropping a failed attempt or cherry-picking a later passing G2 subset cannot publish an unqualified product percentage |
| C24 · Renderer/document identity | A UI cell is observed across navigation, reload or Bun recovery | The collector binds the actual Host-owned WebView/window identity **and** its Host-owned navigation/document generation and the pinned app page identity to the initiating action and observed UI result. A stale renderer message, post-navigation old document or foreign page cannot provide a new successful product UI cell; until GH #541/#552/#542 generation/channel enforcement is qualified, UI-cell acceptance remains `unknown` |

A `pass` is never awarded by a source-only or mocked fixture. **Verdicts remain constrained by GH-532/566 v1 admission:** a qualified, cited `fail` requires a manifest `expected_verdict:fail` with exactly one `implementing_ticket` or `intentional_divergence`. An uncited/not-attempted/inconclusive cell is `unknown`, and a `fail` record for an expected-`unknown` cell is rejected with `RecordMismatch`. When a cell expected to pass actually fails, its mapped conformance test must turn RED; an owner-reviewed manifest/denominator/receipt update with citation and red-cell key is required before a matching `fail` record can be admitted. Never silently flip record verdicts to turn a failing test green. Existing GH-532 red-until-implemented fixture semantics stay separate: a **test** can pass while the product operation's record correctly says `fail` or `unknown`.

## 4. Design

### 4.1 First-principles decomposition and ownership

| Atom / one owner | Input → output | Independent failure oracle | Dependence |
|---|---|---|---|
| Corpus input, GH-532/566 | Committed manifest bytes → digest, v1 kind, cells, one Electron pin | Flip a byte, duplicate cell, invalid kind | Records consume the digest, never define it |
| App source, product harness | Independently approved, code-registered app-id and complete pinned repositories/commits, lockfiles and optional immutable patch → actual prepared app files | A different but internally consistent source pair, missing webapp component or hash/patch mismatch before execution | Does not mint a Keld permission or runtime identity |
| Host state, KEL-78/#588 | Retained verified permissions + genuine successful link → effective profile at a Host-minted generation | Reject before bind, stale G1, mislabelled G2 | Consumer cannot infer state from a broker response |
| Runtime identity, existing supervisor | Actual Host/Bun image + pinned Keld/Bun/engine/platform → observed execution identity | Independent executable/OS read differs from record | The executable digest is **not** the corpus manifest digest |
| Physical observer, X02-T4 | Role- **and WebView/document-generation-bound** initiating action plus correlated file/UI effect completion → app-visible and OS-visible independent effect | Console spoof, mock, no file change, no dialog, delayed G1 effect blamed on G2, stale renderer after navigation | Requires live app + Host admission and the existing GH #541/#552/#542 navigation/channel owner, not merely HELLO |
| Receipt consumer, X02-T5 | Trusted Host origin + causal generation-bound cells + retained attempt census → product receipt and paired records | Forged app output, stale generation, uncovered cell, cherry-picked run | Existing `Corpus::validate_product_run` checks labels and coverage, but does not select/audit attempts |
| Scorer, KEL-74 | Valid receipt+records+committed denominator → board | Mixed profile, missing cells, unknown id | No alternate percentages or a cross-kind score |

The exact trust boundary matters. A Legacy Bun role is *uncontained* and may have same-user ambient filesystem and process access. A JSON file with chmod 0400/0600 owned by that user is therefore **not** itself an authenticity proof. The trusted observer obtains typed, in-process Host-origin admission facts from the actual Host installation path through a collector-controlled callback or one-way authenticated observation seam, **not** from Bun stdout/stderr, renderer messages or app-authored files. Separate actual OS file/UI observations substantiate the claimed app behavior.

**Two different claims are mandatory.** For a *cooperating upstream app*, an independently controlled Host+test harness can make a bounded **behavioral** observation and publish its collector-produced transcript to a content-addressed immutable CI artifact; the receipt/report must name that limited trust assumption and the measured source/runtime identities. For an *adversarial same-UID Legacy app* that may compromise local user-owned files or processes, this bounded observer is **not proof of unforgeability**. Such an authenticity claim must remain `unknown` without separately demonstrated stronger OS-principal separation or external attestation custody. Neither a hash, locally accessible signing key, file permission, nor a self-reported `origin:host` string upgrades the bounded claim.

Rejected alternatives: treating console output as source of truth; accepting app-emitted process IDs or profile strings; copying `ProfileState`→label mapping into another crate; a second signed or JSON-backed runtime authority protocol; a single `app_run` enum addition; stretching `artifact.sha256` to mean an executable or source tree; inferring Legacy from Electron `sandbox:false`; extending a same-UID file mode into a cryptographic guarantee. No new production `unsafe` or dependency is authorized.

### 4.2 Physical manifest and denominator partitions

`keld.compat.corpus/v1` contains one `kind` per manifest. Do **not** alter the parser or claim one v1 physical id can mix operation kinds.

| Logical `electron-apps-v0` family partition | Physical `corpus_id` proposed for X02-T6 | Exact `kind` | First first-proof cells |
|---|---|---|---|
| Install | `electron-apps-v0-install` | `install` | `<app-id>.install`; initially unknown until KEL-141 |
| Activation | `electron-apps-v0-activation` | `activation` | `<app-id>.activate` |
| Primary workflow | `electron-apps-v0-primary-workflow` | `primary_workflow` | `<app-id>.open`, `<app-id>.edit`, `<app-id>.save`, `<app-id>.close-unsaved-prompt` |

`<app-id>` is a registered, fixed manifest identity, not an untrusted user-supplied path. Draw.io is the first intended app. KEL-78 R1 records *planned* desktop/webapp source commits; no execution, patch-result hash, observer or product pass is assumed here. X02-T4 must bind each approved app id to an **independent, code-owned reviewed complete source identity**, not accept commits only because a receipt self-reports internally matching hashes. One physical v1 manifest has one `panel:product`, one kind, a reviewed and committed denominator and `artifact_digest:manifest_bytes`. It retains GH-566 `engine`, `platforms`, `upstream`, `doc_snapshots` and `cells` fields and the existing 44.4.5 pin. No new per-cell `kind` or source/receipt key is smuggled into the closed v1 manifest.

`electron-apps-v0` is a **report grouping**, not an aggregate KEL-74 `Scoreboard` or a currently committed physical corpus id. Each partition scores independently under the existing rules. An overall product or cross-kind percentage requires a separate approved aggregation owner; a passing workflow partition does not erase an unknown install partition. `full_feature` is intentionally deferred and not represented by a fabricated empty corpus. If the owner wants a single physical `electron-apps-v0` identifier instead, a separate public v1 schema/denominator amendment and migration proof are required; this spec selects the simpler backwards-compatible partition approach for review.

### 4.3 App-run cell oracles

| Operation and kind | Controlled stimulus | Independent positive observation | One explicit RED mutation |
|---|---|---|---|
| `install` / `install` | Install an actual KEL-141 built distribution in a fresh OS-owned namespace | Installer exit and OS package/application registration plus digest of the installed image equal the selected prebuilt artifact | Substitute a `.keld/dev` staged Host; install remains unknown |
| `activation` / `activation` | Start the pinned app without a previously opened app window | Host observes the app's own first loaded document, live admitted role and completed application initialization; no fatal evaluation | Replace the app document with a healthy blank test page; activation cannot pass |
| `open` / `primary_workflow` | Open a controlled file from the real app action | App's document model/visible content bound to that exact file identity and contents | Dialog success but file not loaded; test fails |
| `edit` / `primary_workflow` | Make a unique in-document edit | Different model/visible content before and after actual app input, bound to the active document | Emit a fake keystroke/edited event with no state change; test fails |
| `save` / `primary_workflow` | Save the edited active document to a controlled target | Independent readback of target bytes/semantic content matches the unique edit | Fake save event without committed bytes; test fails |
| `close-unsaved-prompt` / `primary_workflow` | Make another edit after save and close the dirty document | The pinned app's actual decision UI is observed (native or in-page as source specifies); Cancel retains the dirty document, and Save/Discard has its independently checked effect | Auto-close on dirty state or a test-owned imitation prompt with no app state transition; test fails |

The oracle binds app source behavior as documented in **the complete pinned app source closure**; it must not invent draw.io file paths or claim Electron normatively specifies the app's Open/Save semantics. A GH-532 citation must support the **particular** Electron contract actually exercised (for example a pinned, relevant dialog/lifecycle API), *in addition to* app-specific real-OS facts. A generic Electron dialog citation does not by itself qualify draw.io Open/Edit/Save or a dirty-close UI. If a source-pinned **app-specific** behavioral oracle has no applicable normative Electron page in the existing citation grammar, it stays `unknown` until the GH-532/GH-566 owning specification explicitly admits a reviewable source-oracle form with independent evidence and a failing negative control; GH-587 does not silently relax that parser.

Action order is observable: install (when available) → activation → open → edit → save → **new dirty edit** → close attempt → prompt decision. The controlled fixture generates unique data and observes effects without a wall-clock sleep. Each asynchronous action retains a **Host-bound initiating role generation and unique causal request identifier** plus independent completion/effect witness, so a G1 request whose disk or UI effect appears after G2 becomes current cannot be counted as a G2 success merely because G2 is current when the observer sees it. A GUI-cell action also binds the actual Host-owned **WebView/window identity and navigation/document generation**, plus pinned app page identity, from the existing GH #541/#552/#542 owner. A cross-document navigation or reload changes the relevant generation; late messages from the old renderer/document cannot count. If role or document-generation attribution is ambiguous or implementation is unqualified, mark the cell `unknown` and/or re-run with a new active generation and distinguishable input. One run's cell results are not silently replayed onto another app revision, Host generation, page generation, platform or artifact.

### 4.4 One ProductReceipt consumer contract (X02-T5)

This is the only **product-corpus receipt**, not a new Keld IPC message or an authority-grant file. `tests/support/corpus_runs.rs::ProductReceipt` is the pre-existing test-side minimal typed view; the X02-T5 implementation must extend its owning parser/validator rather than define an alternate receipt. The stored envelope's proposed closed schema identifier is `keld.compat.product-receipt/v1`.

Logical fields (the eventual serializer must reject missing/unknown/duplicate fields, oversize and malformed byte encodings):

| Field | Owner / accepted meaning |
|---|---|
| `schema` and `corpus_id` | Closed receipt v1 schema, exact physical manifest id; no logical-group alias or mismatched denominator |
| `manifest_sha256` | Exact committed manifest bytes, matching denominator `corpus_sha256` and every record `artifact.sha256` |
| `app_source` | Complete immutable upstream **source-component set** (draw.io desktop and webapp separately), each repository/full commit and pinned lockfiles/dependency closure; `patch` = null or one committed content-addressed edit plus exact pre/post-apply verification; these **never** replace `manifest_sha256` |
| `run_platform` / `run_arch` | Actual observed OS/architecture, matching each record and manifest admission, not a fixture's free-text claim |
| `runtime` | Independently observed Keld source commit and Host executable-image SHA-256, actual Bun version **and running Bun executable-image SHA-256**, and manifest-declared engine token with measured pinned revision; bind each measured image to its actual live process, image selection and observation time, rejecting unresolved races. These digests remain distinct from `manifest_sha256` and the verified policy digest |
| `host_session` | **Collector-assigned, observation-only Host-instance correlation** bound at the externally observed Host spawn to its OS process/start identity, owning collector run and lifetime, plus the initially retained verified policy snapshot digest. The current implementation has **no demonstrated externally serialized Host-session ID**; this proposal therefore must not invent a Host-minted principal/token or treat the correlation as authorization. Independent issuer/custody, unique per-incarnation nonce and exact run/Host lifetime checks reject stale or replayed observations; no Bun-selected string is accepted |
| `run_attempt` | Harness-owned stable opaque run ID and monotonic attempt index, bound **before** action to this exact physical corpus id, source closure, observed OS/arch, Keld/Bun images and authority-profile plan; the attempt's terminal result is retained even after a rerun. It is report correlation data, not a Host principal or second authorization identity |
| `generations` | Ordered, unique Host-origin admission facts for the same Host session: **collector-assigned, nonauthoritative correlation key** bound internally by the Host to the opaque `RolePrincipal` and generation/attempt owner; existing Host-owned window/WebView identity and navigation/document generation for GUI operations; requested profile and **effective** `unverified/legacy/strict`; original verified permissions SHA-256, observed bound/current/running/reader-install milestone and optional subsequent retirement/revocation event. Never serialize a `RolePrincipal`, possession token or invent rival generation authority |
| `cells` | **Nonempty, unique** `(operation_id,oracle_id)` coverage keys with Host-confirmed initiating **role and GUI document generation**/request correlation **and** independently attributed matching effect completion. Initiation must occur while that role and relevant document are live/current; late G1 effects during G2, stale renderer or foreign navigation cannot be attributed to G2/current document. A boundary-spanning ambiguous operation is `unknown` or retried with current-generation-unique inputs. Later honest retirement does not erase completed G1 evidence. No independent verdict/label map—existing `EvidenceRecord` supplies verdict, GH-532 mapping supplies the label |
| `collector_provenance` | An independently validated collector origin/custody fact, not a naked JSON string asserting `host`; acquisition and immutable final artifact must be demonstrably outside the untrusted child-output path |

Generation data is logically an ordered set of **Host-owned** admission facts. The actual `RolePrincipal` and generation owner are intentionally opaque and remain compared inside the Host; the collector receives only a harmless correlation key *after* matching those identities, associated with its independently observed Host instance. G1 and G2 share the frozen verified source policy digest, but each must have an independent actual binding **and candidate-specific effective-profile observation**. The producer must witness the matching Host incarnation (not merely a recycled PID or self-reported JSON ID), principal, generation attempt, live/current state and correctly installed reader under the owning transition lock—not a stale early `Ok`, a poisoned-lock fallback or a successful `is_current` shortcut. An accepted G1 does not qualify G2. A G2 broker success **alone** cannot distinguish `Legacy` from `Unverified` and may not promote either by inference. **Two rejection cases are distinct:** a receipt's claimed G2 state that contradicts the actually witnessed Host state is a *forged/incorrect receipt*; a genuinely observed G2 `Unverified` under the **same frozen explicitly Legacy-requested Host session** is an **admission-policy failure** and cannot score a successful product run in either profile. Preserve that actual Unverified observation as an anomalous/failure diagnostic and reject the mismatched successful receipt. A **new fully retired, no-profile Host session** may validly admit and retain Unverified behavioral evidence, without relabelling. If no trusted effective-state witness exists, do not serialize an assumed `Legacy` success.

**Time semantics:** every successful cell is bound to a generation that was Host-confirmed active/current **at that operation's observation time**. Once G1 retires, its already completed observations remain historical evidence, but **new** post-retirement G1 events are rejected; a newly current G2 may contribute only after its own real installation and Host-origin effective-state receipt. A live G1 need not be retired merely to emit its first verified observation; the later terminal state is recorded when it occurs. Reject duplicate/overflow correlation attempts, pre-bind/future events, stale replay, a cell with no authenticated contemporaneous generation and any post-revocation success—not valid historical G1 events.

The producer moment is not `parse_manifest`, `whenReady`, stdout or `admit_uncontained` alone; its policy decision does not prove the child actually launched. The Host-origin fact becomes eligible only after its actual validated policy, role/Guardian ownership, authenticated link and **current** installed router/reader succeed. The witness is rechecked for each new bound generation. On failure/retirement the collector records a later terminal fact and refuses **new** success events from that generation; it does not revoke previously valid completed operation evidence. The existing host/session owner in KEL-78/#588 supplies this fact through its trusted internal path; X02-T5 owns receipt reading and matched product-cell collection. Neither invents a new application-visible IPC capability.

For offline CI, a purported receipt must be traceable to a qualified collector's retained in-process Host observation and independently corroborated OS behavior, with immutable final artifacts. This can support only the explicitly documented **cooperative-app** behavioral trust claim. A **hostile, same-UID Legacy app** provenance claim instead remains `unknown` without independently demonstrated stronger custody/attestation (for example a separately authorized principal or external collector). No `pass` in either class comes from an unverified file path or locally editable “signed” string alone.

### 4.5 Record mapping, failure, and platform rules

The new X02-T5 reader first authenticates collector provenance **and** rejects an empty receipt cell set, duplicate receipt `CellKey` values, missing/foreign role-or-document generation bindings and actual-observation-time mismatches. These checks are **not yet implemented** by the existing minimal `ProductReceipt { state, cells }` / `Corpus::validate_product_run` pair: `[A,A]` with one record A and `[]` with zero records can otherwise slip through the membership loops. GUI cells additionally require the Host-owned WebView identity, navigation/document generation and pinned app page source; no new renderer generation counter is minted by the collector. Only after the reader passes does it construct the existing `ProductReceipt` view and call `Corpus::validate_product_run` followed by the KEL-74 scorer. Both `state.required_label()` and `AuthorityProfile::as_str()` remain owned where they are. Records/manifest must match platform, arch, pin, engine, exact manifest digest, operation generation and covered cell set. The new reader must also reject **mixed actual Keld/Bun versions, executable image identities or app source pins within one run**, because existing KEL-74 scoring currently compares the manifest digest, authority state and engine identity, not these additional execution identities.

Because the existing adapted `ProductReceipt` exposes **one** `ProfileState`, a run spanning G1 and G2 may be scored together only when *all contributing generations have the same authenticated effective state*. Different valid independently admitted **Host sessions** (or separately qualified profile-bearing roles under their existing owners) require separate product runs/record sets or a typed rejection. **Do not treat a profile-state mismatch between G1 Legacy and G2 Unverified inside one frozen explicitly Legacy Host as a legitimate split-run success**: it violates KEL-78's immutable requested-state admission contract and must be retained as an anomaly with no successful product cell. Never take G1 Legacy as the label for G2 Unverified, average mixed authority, drop Unverified diagnostics, or silently relabel a successful broker call. An asynchronous save initiated by G1 cannot become a new G2 success merely because its filesystem effect appears after G2 is current; require request/commit attribution or use an explicitly `unknown` boundary result and an independently distinguishable G2 retry.

**Attempt publication:** one product receipt is tied to a predeclared harness `run_attempt`; the owning X02-T4/T6 reporter must retain a complete, content-addressed **attempt census** for every evaluated physical corpus/source/OS/profile combination, including failed, aborted and `unknown` attempts and any G1/G2 split. Before test execution, the named owner records an exact deterministic run-selection policy for each partition/lane (for example, the first qualifying attempt); subsequent diagnostic retries remain visible, but cannot silently replace a failed selected result with a later passing G2-only subset. A mixed-state split keeps the original attempt association. X02-T5 validates coverage and attempt linkage before handing *one* admitted record set to the existing scorer. An aggregate percentage, cherry-picked latest success or exclusion of a failed attempt is **not** justified merely by scoring an internally consistent single record list; without a reviewer-approved complete attempt selection, no product completion/percentage claim is admitted. No new authority to mint role identities is introduced by this test-reporting census.

Do not change `validate_harness_run`, conformance `LegacySandboxOff` convention, or the existing fail-closed `ProductRecordsNeedReceipt` until the product reader and its negative controls are integrated in the same vertical implementation. A syntactically valid data-only JSON or a test-local constructed `ProductReceipt { state, cells }` is **not** an authenticated Host fact.

macOS is the first real device, using WKWebView; Windows and Linux enter only with their own actual-platform receipts and qualified observers. CoreGraphics Screen Recording permission enables a specific window observation but its absence on a CI runner cannot be disguised as a pass. Current Mac Legacy gives no zero-ambient-OS-authority guarantee. Windows/Linux profile-selection qualification cannot be inferred from Mac. Missing install and unavailable app automation remain `unknown`. A genuine observed failure is admitted as a `fail` record **only** after its manifest cell has the required citation and expected-fail key; otherwise the mapped test remains RED and the record cannot be reclassified silently.

### 4.6 App-source patch and product-id admission

When a target needs `config + 1 edit`, every contributing repository stays at an immutable full commit pin, including draw.io's **separate desktop and webapp** repositories. KEL-78 R1 names desktop `2edf9fb97eff9bd94bdda33abfe1ee9e7f7bb55e` and webapp `24b76c2cbd55d88e354042e8d329a2e4708972bc` as a **planned** first-proof pair, not an executed receipt. The allowed edit is the planned asynchronous close-with-unsaved dialog replacement inside the existing handler, plus the separately declared configuration changes. One content-addressed, committed patch object (immutable git URL + SHA-256) binds an explicit **allowed path-and-hunk census**: every actual modified file is verified against approved configuration paths or the **single** reviewed behavioral edit; a single patch container with two unrelated code changes is rejected. Record the exact before/after file identities, dependency lockfile/install resolution and applied-tree SHA-256; an undeclared file, unpinned webapp component or lockfile drift rejects the run. A patch is applied and its effects verified before execution; the source/patch identities are sidecar receipt fields, never substituted for the committed corpus manifest digest. If no edit is needed, `patch=null`. A patched run is **not** an unmodified-upstream claim; label it accordingly.

X02-T6, not this draft, proposes a product id as committed only through one reviewed code change to `DOCUMENTED_COMMITTED_PRODUCT_CORPORA` in `crates/keld-compat/src/evidence/scoring.rs` **and** a matching documented `docs/engineering/compat-scoreboard.md` entry, along with the committed v1 manifest/denominator, registered live cases, provenance-validated product receipts where product runs are claimed, and immutable cell evidence. Its PR must record an **accountable, explicit GitHub reviewer handle**, approval on the **exact admitted manifest/denominator/receipt/source revision**, and the outcome of the independent source-and-OS evidence review; an anonymous “reviewed” flag is not sufficient. **There is no existing automated code-to-scoreboard committed-product census:** X02-T6 must add a dedicated fail-closed test that rejects whitelist-only or documentation-only registration, and a CI gate that checks a valid registered product identity has an attributable reviewed approval receipt, before admitting any new id. A truthful `unknown` or pending/red cell may remain committed as a gap, without turning it into a product `pass` or `complete`. An empty, missing, not-yet-measurable or externally uncommitted partition never yields an overall complete/100% claim. The whitelist must not be updated in this specification PR.

### 4.7 Authority, transport, fallback and runtime seam

- Permission-model change: **none**. Retained `keld.permissions.jsonc` stays the only profile request; no new grant or renderer right.
- IPC/wire change: **none** in this spec. The Host-origin product evidence path consumes existing validated runtime ownership; no public IPC event or child token is specified.
- New runtime/OS role: **none**. Do not duplicate a Guardian or attach to another owner's session.
- Compatibility fallback: not required for a feature never admitted. Unverified receipts are preserved truthfully, not dropped.
- Performance claim: none. Future collector serialization is cold test/observation work; it must not add a per-frame or broker hot-path requirement.
- Cancellation/crash: a cancelled install, fatal module evaluation, pre-bound death or missing observer produces no `pass`. A host-session/role recovery cannot accidentally inherit an earlier generation's collector success; the observable records a distinct G2 admission and actual new operations.
