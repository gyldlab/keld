# Electron Compatibility — Keld's Go-To-Market Spec

The target falsifiable promise: **a median Electron app runs on Keld by changing
configuration, not code.** This is the Rspack/Rolldown lesson applied to desktop (see
`docs/research/library/agents-tooling/05-rust-wave.md`).
"Median" is defined and measured, not vibed: we maintain an identified corpus of
open-source Electron apps and publish operation-level evidence only for committed
corpus members. The proposed first draw.io proof includes **configuration plus
enumerated, separately gated macOS-only source adaptations** (#499); its exact
source and native receipts must support any unmodified-source claim.
Static migration estimates are not product compatibility scores.

## 1. The developer experience (the whole flow)

```bash
cd my-electron-app
bunx keld migrate           # target: read-only static analysis and report
bunx keld migrate --write   # target: approved, reversible owned changes only
bunx keld dev               # it opens. unsupported calls fail loudly with fix-its.
bunx keld build             # signed installers + delta-update feed
```

`keld migrate` output (illustrative **target shape**, not an executed command;
`migrate` and `build` remain reserved with `KELD-CLI-045`):

```
Keld migrate static analysis — my-electron-app
  static estimate, not a compatibility score
  ✔ supported calls: <count>   ▲ behavior notes: <count>
  ✘ unsupported calls: <count>   unclassified: <count>
  planned (not written): keld.config.ts · keld.permissions.jsonc · package.json
  not generated: keld.build.ts (build reserved, KELD-CLI-045)
  not generated: keld.compat.ts (no schema/reader)
  not generated: bunfig electron alias (package dependency is the resolver)
  removed if present under --write: tsconfig paths.electron (second resolver)
  blocked if effective tsconfig/jsconfig mappings redirect Electron imports (inherited/wildcard inputs included)
  authority: explicit legacy requires separate consent; zero-authority claim forfeited
  dropped inputs: Chromium switches / disableBlinkFeatures / updater setFeedURL (reasons printed)
  next: approve diffs and run real macOS Host/GUI acceptance; no product PASS inferred
```

| `keld.permissions.jsonc` | unique root `profile` and exact literal grants (03-security, #586/#588, #541/#552); Legacy is never implicit | future `keld migrate --write` |

No `keld.build.ts` (reserved build verb), `keld.compat.ts` (no live reader),
`bunfig.toml` alias or generated tsconfig/jsconfig Electron resolver mapping.
The pre-existing root `compilerOptions.paths.electron` removal requires an
explicitly approved, owned, reversible `--write` change. Qualification also
checks the effective inherited and wildcard mappings for all five Electron
specifiers; removing one literal key is insufficient. Other conflicting
configuration is diagnosed with its source/owner and refused, without granting
new writes to shared, inherited or third-party config or generating an override.
The report names every omission and reason.
No `src-tauri/`, Rust files or new IDL in the first-proof migration path.

`keld.config.ts` **current normative root shape** (not the former nested
`defineConfig({app,runtime,windows,...})` concept sketch):

```ts
export default {
  name: "MyApp",
  entry: "src/main.ts",
  renderer: "index.html",
};
```

For a macOS Electron facade, the approved #446 form instead declares
`initialWindow: "none"` and **omits** `renderer` so the app owns window
creation. The current CLI emits schema 2 and the macOS Core/Host path selects
`HostInitialized` without an initial renderer. This source support does not
establish delivery of the original draw.io graph or its native workflow.

Before app or dependency evaluation, #499 supplies the approved installed
package/lock/file and effective-resolution evidence; the existing staging and
Host launch path consumes it, bound to the actual delivered graph on every
generation. #593 owns the independent no-runtime-auto-install spawn prerequisite.
A root dependency key, the no-install flag or a package duplicate guard cannot
substitute for this admission. Missing, foreign, nested-shadowed or changed
inputs refuse with the owning typed Keld diagnostic before candidate evaluation.

The existing CLI boot/package owner must also deliver the entry-relative code,
preload and assets and the qualified canonical SDK/KIPC transport instance. The
dev stage is nested under the project, so upward package lookup remains part of
admission; entry-only staging does not supply arbitrary sibling files. Equal
transport bytes do not prove import/preload identity or early capture. These
remain implementation gates in the [GH497 output contract](../specs/gh497-first-proof-migration-output.md),
separate from declaration edits and documentation approval.

## 3. How the shim works (layers)

1. **One package resolver**: the installed dependency named `electron` aliases
   `@keld/electron` (#502). Its bare name and `/main`, `/renderer`, `/common`,
   `/utility` subpaths map through package exports to one synchronous physical
   entry for CommonJS require and ESM imports. No plugin, Bun alias or
   tsconfig/jsconfig mapping replaces that resolution.
   `process.versions.electron` is shimmed; `process.type` reports
   `browser`/`renderer` appropriately.
2. **Main-process modules** (`app`, `BrowserWindow`, `ipcMain`, `dialog`, `Menu`,
   `Tray`, …) are TS classes over `@keld/api` kipc calls; event semantics (ready,
   window-all-closed, activate, before-quit ordering) replicated against a conformance
   suite extracted from Electron's documented behavior + fixture apps.
3. **Preload & renderer**: Keld injects a compat user-script implementing
   `ipcRenderer`, `contextBridge` (mapped to real isolated-world exposure where the
   engine supports it, documented emulation otherwise), `webFrame` subset. Preload files
   run in the webview before page scripts, same as Electron.
4. **Host-side emulation** (`keld-compat` crate) for things JS can't fake: `protocol`
   (custom schemes registered into the engine), `session` (cookie/proxy/cache subset),
   `webContents` routing identity, window parenting/modals, `nativeImage` codecs.
5. **Behavior notes**: compat divergences are recorded against named operations
   in the scoreboard, not invented as `keld.compat.ts` flags. That file has
   no live schema or reader and is not a migration output.

**v0 (KEL-72):** `packages/@keld/electron` is a real TypeScript package.
`app.whenReady()`, `app.quit()`, and `window-all-closed` are backed by
`keld_core::LifecycleSession` over `LIFECYCLE_CHANNEL` — not
`Promise.resolve()` stubs. `process.versions.electron` is `"0.0.1"` (Keld's
crate version, not an Electron release) and `process.type` is `"browser"`
in this main-process package. The Electron `app` facade delegates to
`@keld/api`'s singleton lifecycle link, which uses `@keld/kipc`'s
Worker-owned transport; the shim does not open a second link. Bundler-side
alias (`keld build`) is deferred because `keld build` is not live.

Match (scoreboard ✔): with no `window-all-closed` listener, a host
`LastWindowClosed` event quits the app — Electron's documented default
([`event-window-all-closed`](https://www.electronjs.org/docs/latest/api/app#event-window-all-closed)).
A registered listener owns whether the app quits (no auto-quit). Recorded on
[`docs/engineering/compat-scoreboard.md`](../engineering/compat-scoreboard.md).

Divergence (scoreboard ▲, not a §5 quirks-flag toggle): Electron
[`app.quit(): void`](https://www.electronjs.org/docs/latest/api/app#appquit)
is process-lifetime and not thenable. Keld's `app.quit()` returns
`Promise<void>` so callers can observe `KELD-IPC-*` when the Quit Call fails
on the transport. Restoring `void` would paper over kipc; the Promise is
the public contract for this slice. Like Electron's, it returns at once and
never parks the caller (PANEL-P2, #419; GH-528 T3). The role's link closes
when the host's `LifecycleResponse::Quit` REPLY settles. Recorded on
[`docs/engineering/compat-scoreboard.md`](../engineering/compat-scoreboard.md).

Divergence (scoreboard ▲, GH-528 T3): the role's link runs in the GH-527
transport Worker, and a realm opens one link. So `app.whenReady()` rejects with
the typed error that failed or ended that link, and keeps rejecting with the
same error. A failed connect is never retried, because a retry could only
surface `KELD-IPC-005`. The error keeps the real cause:
- a connect failure keeps its own code (`KELD-IPC-001`, `-005`, `-006`, `-007`);
- a link that was up ends with the failure that ended it (`KELD-IPC-003`,
  `-005`, `-006`);
- a plain close is `KELD-IPC-022`.

Historical dev experiment: Bun 1.3.14 did **not** remap runtime
`import "electron"` from `bunfig.toml` `[alias]`; the v0 test fixture
used a `tsconfig.json` `compilerOptions.paths` workaround. Neither
workaround is emitted by migration: #502 owns the single installed-package
resolver with one self-contained entry for ESM/default/CommonJS forms.
The current package exports a `BrowserWindow` subset backed by the
macOS Host-owned native window registry for creation/adoption, selected
geometry and state, close/destroy, and recovery events. Linux and Windows
currently refuse facade-window subscription; this is not a cross-platform
native window backend. Broader Electron behavior and surfaces (`ipcMain`,
preload/`contextBridge`, …) remain later slices. `keld migrate` is not live.

### 3.1 `utilityProcess` and `MessageChannelMain` stay facades

Tier 2's `utilityProcess`, `MessageChannelMain` and `MessagePortMain` must not
introduce a second process model. The Electron facade asks the Keld host to create a
declared app-bound or window-bound role; only the host resolves its bundled entry,
creates the link/principal generation, captures permitted stdio and enforces lifecycle
policy. `fork()` options that would widen process authority are translated to explicit
Keld policy or fail with a scored compatibility result. A returned PID is diagnostic
only, never a Keld identity or control handle.

The host owns every virtual port. Port transfer is one-shot and target-bound, routes
remain host-mediated, and a stale role/webview generation loses transferred ports before
replacement. The facade must reproduce selected pinned Electron oracle queue/start,
message, transfer-validation and close/disconnect behavior; generic routed IPC alone
does not prove compatibility. These contracts are not live in v0.

## 4. Compat tiers & the public scoreboard

- **Tier 1 (v0.2)**: app lifecycle, BrowserWindow core, ipcMain/ipcRenderer/invoke,
  contextBridge, dialog, shell, Menu/Tray, clipboard, Notification, screen, nativeImage
  subset. Exit criterion: electron-quick-start and 3 corpus apps run unmodified.
- **Tier 2 (v0.4)**: globalShortcut, powerMonitor, safeStorage, session subset,
  protocol, webContents surface, `utilityProcess` + `MessageChannelMain` over named
  principalized Bun roles, autoUpdater→keld-update adapter, crashReporter map.
  Exit criterion: ≥ 80% median call-site coverage across the 20-app corpus.
- **Tier 3 (v0.6+)**: `<webview>`→multi-webview mapping, BrowserView mapping,
  desktopCapturer (host capture APIs), net module. Documented-never list published
  (V8 flags, Chromium command-line switches, remote module).
- Scoreboard: `keld.dev/compat` — per-API status (✔/▲/✘ + notes), committed-corpus
  operation evidence per app,
  updated by CI. Honesty is the marketing.
- Operation and workflow evidence (KEL-74) is a separate, versioned ledger:
  each cell binds an artifact digest, platform/arch, Keld/Bun/engine revisions,
  authority profile, and an immutable evidence URI (`sha256:<64 hex>` or an
  `https://` URL with a public host whose path contains a full git object id) to
  pass/fail/unknown/waived.
  Public percentages require a committed denominator (`install`, `activation`,
  `primary_workflow`, `full_feature`) and MUST NOT treat a partial measurement
  as 100% compatibility. Product and showcase panels stay distinct; a named
  stress corpus (including a future VS Code set) MUST NOT redefine product
  tiers. Until a product corpus id is documented as committed, `score` omits
  `unweighted_percent` for `panel: product` and reports `complete` false.
  Parser: `keld_compat::evidence`. Rules:
  [`docs/engineering/compat-scoreboard.md`](../engineering/compat-scoreboard.md).

## 5. Native modules policy

Bun's Node-API implementation is the compatibility path, but a package name or an
N-API source declaration is not a runtime qualification. Each native-addon claim names
the exact package version, Windows/OS architecture, Bun revision, selected/attempted
native-binary SHA-256 (plus the loaded digest for successful rows), operation, oracle,
and authority profile in `keld.compat.evidence/v1`.
KEL-215's Windows x64 fixture records that `better-sqlite3` 13.0.3 (Node-API 10)
passes its SQL/callback/teardown operation on Bun 1.4.2 revision
`744846f844374847c902b5e7fd59b4342a51ef99` with loaded artifact
`e21e5efd71fba66578e95b62554d9028064a80dafd7221bf8a8ef155de8d240a`;
the same fixture records the `better-sqlite3` 12.11.1 JavaScript require succeeding
before native binding load fails during first `Database` construction with
`ERR_DLOPEN_FAILED`. That failed row binds the selected candidate digest
`707a4b480026ccd1fb8e308d43c7248e779d35eeefa09559ec9bb521bb97bb3b`
without claiming it loaded successfully. The immutable
[fixture](https://github.com/gyldlab/keld-benches/tree/5d2db1232c46db6aef0149306a9b766c7a7dd7f1/windows/bun/better-sqlite3-differential)
and [raw receipt](https://github.com/gyldlab/keld-benches/blob/5d2db1232c46db6aef0149306a9b766c7a7dd7f1/windows/bun/better-sqlite3-differential/results/20260911T221908487Z-3044.windows-x64.raw.json)
retain the exact commands, exits, runtime queries, outputs, source/lock digests, and
negative controls. Neither row generalizes to another package version, artifact,
architecture, Bun revision, or operation. Planned `keld doctor` addon guidance will
report only curated, version-qualified evidence rather than promising that a prebuild
loads; the current doctor checks do not scan native addons.
Modules that reach into Electron internals (rare) are Tier-✘ with documented
workarounds.

## 6. Migration corpus (measurement harness)

`corpus/` (separate repo, gitignored fixtures): electron-quick-start, a tray app, a
multi-window editor, an sqlite app, a protocol-handler app, plus community submissions.
Planned corpus CI will run an actual staged/installed application on named OS
lanes with Host/UI/file evidence and a committed corpus ID before publishing
operation results. `keld migrate` is currently reserved and
`keld dev --headless --smoke` is not a live CLI contract; neither may be
listed as a passing CI command or a compatibility-score trend. An evidenced
compatibility regression is a P1.

## 7. Updater bridge (the trap every migrator hits)

Electron→Keld switchers face the same discontinuity as Electron→Tauri (Fluxzy lesson:
users stranded on the old updater). A **bridge release recipe** and feed-server
configuration are later guidance owned separately by #491's updater and release
owners: a final Electron release whose electron-updater feed points at a Keld-built
installer, with both formats served during the transition window.

First-proof `keld migrate` does not generate that recipe or feed-server configuration;
both are outside GH-497's closed output map. Future automatic generation requires a
separately approved owner, exact output map, consent and rollback. Observing
`setFeedURL` grants no updater network authority. The bridge remains a first-class
guide, not a footnote.
