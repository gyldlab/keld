# F03 — webcontents-navigation

_Research unit of the Electron compatibility wayfinder map; generated 2026-10-06; labels [fact]/[inference]/[unknown] as written by the unit agent; two independent refuters (invariants, Electron semantics) reviewed every decision._

## Summary

[fact] The family is 34 entities / 381 members (WebContents alone 195). Corpus demand is narrow and consistent: both draw.io Desktop and Zettlr register `will-navigate` with an unconditional `event.preventDefault()` plus a `setWindowOpenHandler` (Zettlr deny-all; draw.io allows only `about:blank` with `overrideBrowserWindowOptions`), rely on `webContents.send` (49 / 9 call sites), `did-finish-load` (draw.io 7), `loadURL`/`loadFile`, `executeJavaScript` with awaited results (draw.io 5), zoom (`zoomFactor`/`zoomLevel`/`setVisualZoomLevelLimits`), `printToPDF`/`print`, `openDevTools`/`toggleDevTools`, `render-process-gone`, `destroyed`/`did-navigate`/`isDestroyed`, `console-message`, `unresponsive`; no corpus app uses NavigationHistory, Debugger, offscreen, sharedTexture, WebFrameMain frame-tree APIs, or `<webview>` (draw.io's 7 hits all DISABLE it). [fact] Keld today has no WebContents facade at all: keld-wv v0 `WebEngine` = create/navigate/eval(fire-and-forget)/set_bounds/devtools(Open|Close)/destroy; the only navigation observable is `AppWindowEvent::NavigationReady` from wry `PageLoadEvent::Finished`; the only policy hooks are Windows deny-all `NewWindowRequested` + guarded `PermissionRequested` (type-witnessed before first navigation); the KEL-142 macOS bridge supplies the reusable pieces (isolated `WKContentWorld` document-start user scripts, host-owned navigation generation counter, pending-call invalidation on navigation, `KELD-WV-011`). Window registry (H7) is TARGET in keld-core; KEL-79 (origin/resource/navigation/popup policy) is Backlog; KEL-132 is In Progress. Design answer: implement this family ONCE as (a) one engine-neutral per-webview navigation state machine in keld-wv keyed by (WebviewId, navigation generation) that synthesizes Electron's event vocabulary from raw engine signals, (b) guard-first navigation/popup policy (default-deny, app hooks can only further deny; host-initiated loads bypass `will-navigate` exactly as Electron documents but never bypass the guard), (c) `eval` extended with a structured result envelope, (d) preload = host-injected isolated-world document-start script with the Electron sandbox `require` subset, (e) a serialized host print/PDF broker, (f) devtools off in release unless `web.devtools`. Documented divergences (▲): default window.open = deny, devtools default off in release, zoom per-view not per-origin, `render-process-gone.exitCode`/`unresponsive` absent on WKWebView, NavigationHistory `pageState`/`restore` ✘. Never: sharedTexture/offscreen, Debugger CDP in production, device emulation, WebRTC policy knobs, `clone()`, Node-in-webview (`sandbox:false` honoring), trusting invalid certs via `certificate-error`.

## Reuse points

- keld-wv `WebEngine` trait + `WvError` codes (KELD-WV-001..011): extend with the destination `HostHooks` (navigation/popup/title/crash callbacks) and `EvalCallback`; never a second engine abstraction in keld-compat or @keld/electron (crate AGENTS.md: trait changes need design review; new methods land with a live backend).
- KEL-142 `RendererBridgeEndpoint` navigation generation (`navigation_started`, `settle`) and document nonce: the ONE identity for WebContents id/generation, `destroyed`, stale-send drop, executeJavaScript invalidation and WebFrameMain `detached`.
- KEL-142 isolated `WKContentWorld` AtDocumentStart user-script injection (and its WebView2/WebKitGTK counterparts: AddScriptToExecuteOnDocumentCreated async form, UserContentManager) = the preload registration path and the host-owned navigation reporter path; no page-world injection.
- `AppWindowEvent` (NavigationReady, LastWindowClosed) + `keld_core::LifecycleSession` (window_opened/window_closed) = existing event spine to grow into per-webview navigation events; KEL-64 double-rAF beacon stays the first-paint metric (never conflate with did-finish-load / ready-to-show).
- Windows `GuardInstalled` type witness (`navigate_initial` requires it) = the pattern for installing navigation-policy + new-window + permission handlers before first navigation on every backend (KEL-132/KEL-168).
- arch 02 §5 compat mapping: `webContents.send` ⇄ host-routed EVENT on the `el:*` namespace with the SCV codec (KEL-98 echo-codegen owner); `VirtualPortRegistry` for postMessage/MessagePortMain (KEL-75/KEL-80); 4096 B inline + bulk lane for big payloads.
- keld-guard `Principal::Webview{id, generation}` + `web.*` capability vocabulary (web.camera/web.microphone live; web.devtools named in arch 03): add `web.navigate`/`web.popup`/print grants there, never a compat-local allowlist.
- keld-native `FsBroker` verified-manifest/bounded-I/O pattern for printToPDF/savePage/takeHeapSnapshot outputs and dialog-selected scopes (arch 05 §3).
- KEL-74 evidence schema + KEL-237 lifecycle corpus (`crates/keld-compat/fixtures/lifecycle-corpus`) for ordered navigation-event conformance cells; `keld.compat.ts` quirks flags for ▲ (windowOpenHandler strictness is already the named example in arch 04 §3 item 5).
- `@keld/api` singleton app-link (`app.ts`, `link.ts`) and `channels.handle` registry: WebContents facades must dispatch through this link, not open a second socket/reader (KEL-142 §4.3 ownership).
- KEL-135 per-view `WKWebsiteDataStore` / WebView2 user-data-folder identity = `contents.session` identity; KEL-132 GPU `degraded-rendering` fact stays distinct from render-process-gone.
- `keld_wv::DevtoolsAction` + per-backend open/close (wry devtools feature, WebView2 OpenDevToolsWindow) + arch 03 `web.devtools` rule = the devtools surface; no separate dev-flag plumbing.

## Decisions (with refuter verdicts)

### F03-D1 — Where is Electron's navigation event vocabulary (did-start-loading … did-finish-load/did-fail-load, did-navigate(-in-page), dom-ready, will-redirect, page-title-updated, destroyed) produced, and from what identity?

**Proposed answer:** One engine-neutral per-webview navigation state machine in keld-wv, keyed by (WebviewId, navigation generation) and reusing KEL-142's generation counter as the single document-identity source. Each backend feeds raw engine signals (WK: WKNavigationDelegate didStartProvisional/didCommit/didFinish/didFail/didFailProvisional + an injected isolated-world document-start reporter for DOMContentLoaded/hashchange/popstate/title; WebView2: NavigationStarting/SourceChanged/ContentLoading/DOMContentLoaded/HistoryChanged/DocumentTitleChanged/NavigationCompleted(IsSuccess, WebErrorStatus); WebKitGTK: load-changed/decide-policy/notify::title). The machine emits a pinned-oracle ordered sequence; `@keld/electron` only renames and fans out to listeners. `loadURL`/`loadFile` promises resolve on the generation's did-finish-load and reject with the generation's did-fail-load (errorCode/description) — a superseded navigation must reject the earlier promise. `webContents.id` = host WebviewId; `WebFrameMain` identity = (WebviewId, generation, frame token).

**Evidence:**
- [fact] Electron docs define each event only by trigger ('onload dispatched', 'main frame navigation is done', 'document in top-level frame is loaded'); no total order is documented → order must be recorded from the pinned oracle (receipt R1–R4).
- [fact] KEL-142 already owns generation rotation + pending-call invalidation (crates/keld-wv/src/wkwebview/macos_bridge.rs `navigation_started`, `settle(navigation, request)`; spec §5.2 steps 1–6).
- [fact] Current observable is a single `NavigationReady` from wry `PageLoadEvent::Finished` (Started|Finished only) — insufficient for dom-ready/did-navigate/in-page/redirect (wkwebview/mod.rs:693-736; learnings 2026-08-17).
- [fact] WebView2 documents its own partial order: SourceChanged before ContentLoading; ContentLoading after NavigationStarting/SourceChanged and before HistoryChanged/NavigationCompleted; DocumentTitleChanged may run before or after NavigationCompleted (receipt R20).
- [fact] arch 02 §5: 'Webview navigation: principal generation rotates; pending replies to the old principal drop' — the same generation must drive both IPC and events (one rule, one owner).

**Rejected alternatives:** Per-backend ad-hoc emission in @keld/electron or in each backend (three parallel state machines, violates one-rule-one-owner and makes ordering untestable once); extending wry PageLoadEvent (interim scaffolding, only 2 states, being replaced by direct bindings); deriving document identity from URL strings (forgeable, breaks on same-URL reload).

**Confidence:** medium-high on ownership/identity; medium on exact ordering until the oracle recording exists · **Type:** prototype · **Unknowns:** [unknown] Whether WKWebView exposes any delegate for same-document navigations (none seen in WKNavigationDelegate topic list; the injected reporter is the inferred fallback). ### F03-D2 — Who decides whether a navigation proceeds, and what does `will-navigate` + `event.preventDefault()` mean under default-deny?

**Proposed answer:** Guard first, app second, deny-only hooks. The host evaluates every top-level/frame navigation against a generated allow-list (`web.navigate`-shaped origin/scheme scopes; app bundle resources and the app's own origin are implicit) BEFORE the engine commits (WK decidePolicyFor → .cancel/.allow; WebView2 NavigationStarting.Cancel; WebKitGTK decide-policy ignore/use). Only guard-allowed, non-host-initiated, non-same-document navigations are surfaced as `will-navigate`/`will-frame-navigate`, where the app may further deny; it can never widen. Host-initiated `loadURL`/`loadFile`/`reload`/`navigationHistory.go*` bypass `will-navigate` exactly as Electron documents but still pass the guard. Denied navigations produce a stable KELD code + diagnostic, not silence. Default allow-list scope is a user-owned choice (see unknowns).

**Evidence:**
- [fact] Electron: 'This event will not emit when the navigation is started programmatically with APIs like webContents.loadURL and webContents.back. It is also not emitted for in-page navigations' (receipt R5).
- [fact] Corpus: draw.io `contents.on('will-navigate', (event) => { event.preventDefault() })` unconditionally (electron.js:2192) and blocks `about:` in the isolated-world `navigation` listener because 'Navigations to about: URLs never reach will-navigate'; Zettlr denies all but dev `http://localhost:3000` and opens externally (attach-app-navigation-handlers.ts:67-83). A facade that surfaced host-initiated loads would blank both apps.
- [fact] arch 03 §4.3 item 3: 'navigation policy hooks (allow-list)' are always-on webview hardening, 'not in this slice'; invariant 2 forbids a missing handler becoming allow; research 186 #4 shows Electron's handler-dependent allow-by-default is the anti-pattern.
- [fact] Engines all provide a pre-commit veto: WKNavigationActionPolicy allow/cancel/download (R15), WebView2 NavigationStarting 'Navigations will be blocked until all NavigationStarting event handlers return' with Cancel (R20), WebKitGTK decide-policy default `webkit_policy_decision_use()` with deferral via ref+TRUE (R23).
