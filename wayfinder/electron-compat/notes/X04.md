# X04 — security-mapping

_Research unit of the Electron compatibility wayfinder map; generated 2026-10-06; labels [fact]/[inference]/[unknown] as written by the unit agent; two independent refuters (invariants, Electron semantics) reviewed every decision._

## Summary

Every Electron security surface in scope collapses onto four existing Keld owners, none of which needs a new schema: (1) keld-guard `evaluate(manifest, Principal, capability, resource)` with the arch 03 §2 grant shapes (`app.{fs,net,shell,system,secrets,auth}` and `windows.<w>.{channels, web.*}`), (2) the KEL-142 isolated-world bridge (`window.keld.invoke`) in place of preload/contextBridge/ipcRenderer, (3) KEL-75/78 principalized strict roles in place of utilityProcess/fuses, and (4) the arch 06 §4a host-owned signed feed in place of autoUpdater/ASAR. The decisive inversion is Electron's two independent allow-by-default permission paths (request + check) becoming one guard decision where a missing Electron handler is a `KELD-GUARD001` deny and a registered handler can only narrow, never widen. Live today: `/app` grants for `AppProcess` only; a minted `Principal::Webview` is `KELD-GUARD006` until window-level grants ship (KEL-102/T4), and the media callbacks evaluate resource `*` because wry exposes no origin. Three design atoms are genuinely open and need grilling, not more research: the `shell.open` scheme-class grant spelling (draw.io/Zettlr open arbitrary https/mailto URLs and `https://**` is inert by the KEL-208 authority rule), the CSP profile that must admit draw.io's `'wasm-unsafe-eval'`, and the host-minted one-shot `fs.read` grant for OS-delivered file paths (second-instance/open-file). Device permissions (HID/USB/serial/Bluetooth) have no broker, no principal and no spec: documented-unsupported, not legacy. Nothing in this unit auto-selects `legacy`; KEL-78 fixes that Electron `sandbox:false` is not the legacy key and renderer sandbox is a different column, so Zettlr's two `sandbox:false` windows are a scoreboard ✘/▲ requiring a verified preload audit, not a profile downgrade.

## Reuse points

- keld_guard::evaluate(manifest, Principal, capability, resource) + Principal::Webview{id, generation} + DenyReason codes/`fix()` text — the only policy evaluator; Electron permission/check/device handlers become post-decision narrowing filters.
- keld_ipc::guard_dispatch::dispatch_privileged — sole guard-before-handler boundary (KEL-102-D5); shell/deeplink/protocol brokers must route through it, not add a second check.
- URL authority matcher (KEL-208, live in keld-guard) — reuse for `shell.open`, `net.connect`, `windows.<w>.web.<perm>` origin scopes; do not add a regex or second URL parser.
- keld_native::FsBroker (KEL-130) retained scopes — protocol.handle file reads, openPath/showItemInFolder/trashItem, printToPDF output, shortcut links all resolve through it.
- keld_wv::media::media_permission_decision / guarded builders / WebView2 `add_PermissionRequested` registration — extend the kind→capability map (geolocation, notifications, clipboard-read, display-capture, fullscreen, pointerLock) instead of per-platform policy.
- KEL-142 WKContentWorld isolated script + frozen page-world `window.keld.invoke` — the only renderer authority path; `contextBridge`/`ipcRenderer`/preload are user-script layers over it.
- keld_ipc CallError{code, message} + registered KELD-* code rule (arch 02 §2) — ipcMain.handle error replies and `auth.token` constant-message exception.
- `windows.<w>.channels` + `el:*` namespace (arch 02 §5, arch 03 §2) — per-window IPC grants; remote-content windows get `channels: []` by rule, not by app code.
- keld_core::LifecycleSession / LIFECYCLE_CHANNEL (KEL-72) — `web-contents-created`, `before-quit-for-update`, second-instance ordering hang off the same session, no second event bus.
- keld_runtime RoleConfig (exact env, fixed /app cwd, KELD_APP_LINK per spawn) + RoleRegistry generations + VirtualPortRegistry (KEL-75/KEL-80) — utilityProcess/MessageChannelMain facades and the fuse analogues (runAsNode/nodeOptions/nodeCliInspect).
- keld_guard::admit / ProfileState {Unverified, Legacy, Strict} (KEL-78) — the only profile machinery; `profile: "legacy"` key (not live) is the single legacy entry point.
- keld-update manifest/feed wire (arch 06 §4a) + KEL-53 transaction + keld-pack ExpectedAppIdentity (KEL-19/KEL-254) — autoUpdater facade, ASAR-integrity and onlyLoadAppFromAsar analogues.
- KEL-135 persistent profile identity — `partition`/`session` webPreferences, cookie encryption analogue, SAVED-GRANT revocation.
- arch 05 broker table modules `shell`, `deeplink`, `dialog` ('scoped-path grants flow into fs scopes') — openExternal, single-instance handoff, and the one-shot file-intent grant reuse the dialog scope flow.
- keld.compat.ts quirks flags + scoreboard ▲/✘ (arch 04 §3(5), keld-compat AGENTS.md) — the only two divergence channels; `ignoreWeakWebPreferences` and `sendSync` policy live here.
- KEL-74 evidence schema + KEL-237 lifecycle corpus (crates/keld-compat) — every negative test here lands as a cell, not a new harness.
- KEL-98 echo codegen — `.k.ts` channel contracts for `el:*` typed channels; no new IDL.
- keld doctor permission explain (KELD-GUARD fix text) and the planned deny recorder (arch 03 §3) — migrate's seeded manifest and `keld dev` fix-its consume the same DenyReason text.

## Decisions (with refuter verdicts)

### X04-D1 — How do Electron's session.setPermissionRequestHandler / setPermissionCheckHandler (and <webview> permission-request) map onto Keld without reintroducing allow-by-default?

**Proposed answer:** One guard decision, two Electron views of it. The host evaluates `windows.<w>.web.<permission>` (same array-of-scopes shape already used by live `app.web.camera`/`app.web.microphone`, moved under `windows` as arch 03 §2/§4 already names) as `Principal::Webview{id, generation}` from the host registry. The facade's request handler and check handler are both invoked AFTER the guard allows and may only narrow (callback(false)/return false => deny); a handler return of true when the guard denied is ignored and emits a dev-warned `KELD-GUARD001` deny with the exact manifest fix. No handler registered => guard decision stands (deny on empty manifest). Check and request return the same value for the same (principal, permission, origin) tuple. Permission-name vocabulary = Electron's documented list mapped 1:1 onto `web.<name>` literals; unknown names deny. Origin scopes use the live KEL-208 authority matcher; until a platform callback supplies the requesting origin (WebView2 `Uri` does; wry does not) the resource stays the `*` sentinel and an origin-shaped grant must not match (already tested in keld-wv `origin_looking_grant_does_not_match_sentinel`).

**Evidence:**
- [fact] security.md: 'By default, Electron will automatically approve all permission requests unless the developer has manually configured a custom handler.'
- [fact] research 186 row 4: request and check are independently allow-by-default paths with different exceptions (geolocation switch, deprecated sync clipboard read).
- [fact] keld-guard lib.rs:705 denies any non-AppProcess principal (GUARD006); lib.rs:1899-1936 tests default-deny `web.camera`/`web.microphone` on an empty manifest and deny `https://evil.example` under a `*` grant.
- [fact] keld-wv media.rs:29-36,57-59: platform callbacks pass no origin; resource is `*`; origin grants unenforceable.
- [fact] arch 03 §4(3): 'Missing identity and AppProcess fail closed (KELD-GUARD007)… A minted webview principal is still KELD-GUARD006 until window-level grants exist.'
- [fact] KEL-132 §3: REVOKE requires navigation generation rotation; SAVED-GRANT (KEL-135 §7.1): a persisted engine Allow cannot bypass the next session's denying policy.
- [fact] corpus: neither draw.io nor Zettlr registers setPermissionRequestHandler/CheckHandler (grep over src/main/electron.js and source/app/**) — so under Electron they run with auto-approve; under Keld they get deny with fix-it text.

**Rejected alternatives:** (a) Honor Electron default (allow when no handler) — violates briefing invariant 2. (b) Let a facade handler returning true grant beyond the manifest — moves authority into Bun, breaks one-owner rule. (c) New per-permission schema block — arch 03 §2 already has `windows.<w>.web.*`; a new block would be a duplicate policy surface. (d) Evaluate as AppProcess with `/app/web/*` — the `/app` grants must never apply to a webview (GUARD007 rule).

**Confidence:** high on the inversion and shape; medium on vocabulary breadth (which of Electron's ~46 permission names Keld will ever expose; most have no host broker) · **Type:** task · **Unknowns:** Exact Keld behavior of saved engine permission preferences on Windows/macOS (KEL-135 SAVED-GRANT awaiting); whether wry will ever surface origin; which subset of permission names gets a host broker in Tier 1/2 (only media exists).

- App-selected autoUpdater feed URL / headers / serverType flowing into the privileged updater: Briefing invariant 10; arch 06 §4a: trust root is the compiled-in key and declared feed base, never feed- or app-supplied.

- Permission handler (request/check/device) returning true beyond the manifest; absence of a handler treated as allow: Briefing invariant 2; guard is the sole default-deny owner; handlers may only narrow.
- Electron `sandbox:false` / `appSandbox:"off"` as a selector of Keld `legacy` profile: KEL-78: not the key; renderer sandbox is a different column; no auto-downgrade.
- Full Chrome DevTools Protocol / inspector in production webviews without `web.devtools`: Research 13 never table; arch 03 §4 'devtools off in release unless web.devtools: true'.
