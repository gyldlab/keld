# X05 — performance-and-faster

_Research unit of the Electron compatibility wayfinder map; generated 2026-10-06; labels [fact]/[inference]/[unknown] as written by the unit agent; two independent refuters (invariants, Electron semantics) reviewed every decision._

## Summary

Answer to "backward compatibility AND better performance, faster": compatibility is bought by cloning Electron's observable contract in a TS facade over kipc, and performance is bought by what the facade does NOT ship (bundled Chromium, Electron main-process stack). The two meet at one cost model: every Electron main-process call that is synchronous in Electron and needs host state becomes either (i) a blocking CALL (one kipc round trip, Windows Bun<->Rust diagnostic p50 ~47 us / p99 ~101 us vs 100 us budget, not publication-eligible; macOS/Linux Bun arm unmeasured; Rust<->Rust macOS library arm p99 9.25-9.6 us), (ii) a facade-side state mirror answered synchronously and kept coherent by host events carrying a generation/sequence stamp (write-through on setters), or (iii) an async-only divergence (▲) that changes the caller contract. Evidence says: [fact] the corpus does use sync getters in time-critical paths (draw.io persists getSize/getPosition/isMaximized/isFullScreen inside a close handler; 6 isDestroyed guards), [fact] Zettlr has 6 sendSync sites and 186 ipcRenderer.invoke sites, [fact] KEL-142's live minimum renderer bridge admits exactly one pending invoke per WebView, so the ipcRenderer facade cannot reach L1 for Zettlr until bounded multi-pending correlation (KEL-80 owner) exists. What gets cheaper is measured only narrowly: [fact] 78% lower main-process RSS in one Windows direct-COM session (total RSS NOT lower there), [fact] Bun bootstrap 53.3% sooner / 42.8% lower RSS in a narrow VS Code extension-host PoC, while [fact] Electron led first paint 275 ms vs Keld 469 ms (Chromium controller-creation floor, KEL-62). No compat-overhead lane exists in gyldlab/keld-benches (README fetched 2026-10-06), so facade cost today is a model, not a measurement; the plan is a same-app Electron-vs-Keld lane under KEL-90/KEL-129 census rules with p50/p95/p99 block-bootstrap and three never-blended claim classes (measured / target / projection). "Faster" delivery comes from parallelizing families that own disjoint crates/packages (native-desktop brokers, windowing registry+mirror, updater adapter, session/protocol transport) after one small serial step: a single-owner kipc channel-id and guard capability-name allocation rule, because keld-ipc frame constants, @keld/kipc transport.ts mirror constants, keld-guard manifest schema, Cargo.toml and root AGENTS.md are single-writer files that every family would otherwise collide on. Conformance entries and fixtures for every Tier 1 family can start now with zero code collision. "Faster" MUST NOT mean skipping conformance entries, widening permissions, retries, sleeps, a Rust rewrite as proof, blending claim classes, or publishing a percentage without a committed denominator.

## Reuse points

- kipc CALL/REPLY with host-minted correlation ids and absolute deadlines (crates/keld-ipc receive.rs/link.rs; kel133 deadline model) - the facade must not mint its own clocks or retry after partial consumption
- @keld/kipc FrameReader + WriteQueue (single serialized writer per link) - the facade adds no second buffer/queue
- @keld/api LifecycleLink and AppChannel<Request,Response> + dispatchApplicationCall - ipcMain.handle maps onto AppChannel handlers, not a parallel dispatcher
- KEL-98 echo-codegen declaration source - typed channel contracts and the TS mirror of channel ids are generated, never hand-copied
- keld-core LifecycleSession window_opened/window_closed/LastWindowClosed - the window registry extends this owner; BrowserWindow 'closed' and app 'window-all-closed' ordering derive from it
- keld-runtime VirtualPortRegistry (PortCapability, one-shot target-bound transfer, MAX_PORT_MESSAGE_LEN 4096, generation revocation) - MessageChannelMain/MessagePortMain and webContents.send routing identity
- keld-runtime RoleRegistry/RoleGeneration - utilityProcess facade (KEL-75); PID is diagnostic only
- keld-guard PermissionsManifest/evaluate/Principal/Decision - every sendSync/invoke/clipboard/executeJavaScript grant is evaluated here before dispatch (guard_dispatch::dispatch_privileged); no facade-side allow
- keld-native FsBroker serve pattern (prepare(VerifiedManifest) -> handle_request) - template for dialog/clipboard/shell brokers
- keld-compat evidence.rs (KEL-74 schema, score, denominator) and KEL-237 lifecycle corpus - compat-overhead results bind to the same cell/digest vocabulary
- gyldlab/keld-benches metric registry schema/metrics.v1.json (PAINT-OPPORTUNITY, MEM-IDLE, IPC-RTT) and §5.1 census rules - new FACADE-RTT lane extends the registry, not a new harness
- keld-wv isolated-world injection (WKContentWorld, KEL-142 §5) - contextBridge/preload emulation lands in the same world, not a second script-injection path
- KEL-62 attribution chain and KEL-83 prewarm lever - Windows first-paint work is already owned; compat must not reopen it

## Decisions (with refuter verdicts)

### X05-A1 — How do Electron-synchronous main-process window getters (getBounds/getSize/getPosition/isMaximized/isFullScreen/isDestroyed/getFocusedWindow/getAllWindows) get implemented without either lying (stale) or blocking the Bun event loop on every read?

**Proposed answer:** Facade-side window-state mirror, host-authoritative: the host (keld-core window registry, TARGET) emits window-state events (bounds, maximize/unmaximize, fullscreen, focus, destroyed) over the app link, each stamped with a monotonic per-window state generation. Getters read the mirror synchronously (zero kipc traffic, zero allocation per read). Setters (setBounds/maximize/...) are write-through: the facade applies the requested value to the mirror and issues the CALL; the host's confirming event (with the new generation) reconciles or corrects it, and a correction emits the Electron-visible event ('resize'/'move'). isDestroyed() and the 'Object has been destroyed' throw are answered purely from the mirror's destroyed flag, set by the host's destroyed event and by local destroy(). Divergence to record as ▲: between an OS-initiated change and arrival of the host event the getter can be one generation stale; Electron reads Chromium's in-process view so it is never stale. [inference] Reads dominate writes in the corpus (draw.io: 6 isDestroyed, 3 isFullScreen, 2 isMaximized, getSize/getPosition in a 'close' handler; Zettlr: 3 isMaximized, 3 getSize, 2 getBounds, 7 'resize' listeners), so the mirror removes nearly all round trips from these paths.

**Evidence:**
- [fact] Electron v44.4.5 browser-window.md: getBounds returns Rectangle; getSize/getPosition return Integer[]; isMaximized/isFullScreen/isDestroyed return boolean (synchronous); 'Reading this property throws Object has been destroyed once the window has been destroyed' (retrieved 2026-10-06)
- [fact] drawio-desktop/src/main/electron.js:828-830 reads win.getSize(), win.getPosition(), win.isMaximized(), win.isFullScreen() synchronously to persist lastWinSize; :107,:149,:902,:1419,:3216,:4375 guard with isDestroyed()
- [fact] Windows Bun<->Rust kipc diagnostic p50 47.6 us / p99 101.6 us per CALL->REPLY (budget-scoreboard.md line 92, KEL-99) - a blocking-CALL getter would spend one of these per read and block the Bun loop while waiting
- [fact] kel142 §6: 'no UI thread blocks on Bun, app-link I/O, or handler completion' - a host-side blocking read of Bun is forbidden, so coherence must come from events, not from synchronous host queries
- [fact] keld-core has no window registry type today (grep WindowRegistry = 0); briefing lists it TARGET

**Rejected alternatives:** (a) Blocking CALL per getter: costs ~50-100 us (Windows diagnostic) per read, blocks the Bun event loop, and Bun's kipc client is an async socket (Bun.connect) with no proven synchronous read primitive - [unknown] whether a sync socket read exists in Bun at all; also violates kel142 'no UI thread blocks' if the host side had to wait. (b) Async-only getters (Promise<Rectangle>): breaks the published contract at every corpus site above (▲ for all of BrowserWindow is not 'compatibility'). (c) Mirror without generation stamps: cannot detect a late event overwriting a newer write-through value; stale-vs-authoritative is undecidable.

**Confidence:** medium · **Type:** prototype · **Unknowns:** [unknown] Exact Electron semantics of getBounds immediately after setBounds on each OS (Windows DPI/min-size clamping may make the write-through value wrong until the host event lands) - the Electron oracle fixture must be run per OS to record the true sequence. [unknown] Whether Electron's isDestroyed() can observe a destroy initiated by the OS before the 'closed' event is emitted (ordering of destroyed flag vs 'closed'). [unknown] Event latency host->Bun under load (the staleness window) - unmeasured.

**Refuters:**
- none

### X05-A2 — Can ipcRenderer.sendSync keep Electron's blocking-renderer contract on system webviews, as KEL-127 directs (blocking CALL with deadline, rate-limited, dev-warned), or is async-only the only honest option?

**Proposed answer:** Treat it per engine and record each as its own scoreboard cell. [fact] Electron: 'Sending a synchronous message will block the whole renderer process until the reply is received, so use this method only as a last resort'; main sees it as the distinct 'ipc-message-sync' event. [fact] WebView2 (Chromium-derived) exposes chrome.webview.hostObjects.sync.* synchronous proxies (Microsoft how-to page shows `chrome.webview.hostObjects.sync.sample.dateProperty` usage), so a blocking renderer->host hop is available there. [fact] WKWebView's documented JS->native paths (WKScriptMessageHandler, WKScriptMessageHandlerWithReply via window.webkit.messageHandlers.<name>.postMessage) are asynchronous; Apple's page describes no synchronous call path. [lead] The only known blocking emulation on WKWebView is a synchronous XMLHttpRequest to a WKURLSchemeHandler-served custom scheme (renderer web-content process blocks while the host completes the task asynchronously); this is unverified in Keld and must be prototyped, including its deadline behavior and whether sync XHR is still permitted on the main thread in the pinned WebKit. [unknown] WebKitGTK path. Proposed contract regardless of engine: the sendSync facade is a CALL on the same guarded channel as invoke, carries an absolute deadline (kel133 model: host-minted Instant, no renewal), is rate-limited in keld.compat.ts, dev-warns once per channel, and on deadline returns a thrown KELD error rather than hanging; where the engine cannot block, the cell is ▲ 'async-only' with a migrate diagnostic naming the site, never a silent Promise. Corpus demand is small but real: Zettlr 6 sites (config-provider get-config/set, citeproc-provider; preload/index.ts:37,57,63,74; pinia/config.ts:28,49), draw.io 0.

**Evidence:**
- [fact] https://raw.githubusercontent.com/electron/electron/v44.4.5/docs/api/ipc-renderer.md: sendSync 'Returns any - The value sent back by the ipcMain handler' and 'will block the whole renderer process until the reply is received, so use this method only as a last resort' (retrieved 2026-10-06)

### X05-A3 — Does the live renderer bridge (KEL-142: exactly one pending invoke per WebView, second invoke fails immediately) allow an ipcRenderer.invoke facade that real apps can use?

**Proposed answer:** No. [fact] Zettlr has 186 ipcRenderer.invoke call sites across 65 files and 25 ipcMain.handle sites; Vue components issue overlapping invokes during mount. Under KEL-142's rule the second concurrent invoke fails immediately rather than queueing, so Zettlr would fail at L1 (basic behavior), not at some semantic edge. The ipcRenderer/ipcMain family therefore has a hard sequencing dependency: bounded multi-pending correlation per WebView (host-minted correlation ids, bounded window, slow-consumer rejection with a typed error, no hidden unbounded queue, stale-reply discard on navigation) must be specified under the KEL-80 owner (virtual channels/backpressure/replay) and KEL-142's §6 rules before any ipcRenderer facade claims BEHAVIOR_MATCH. Electron itself has no documented concurrency limit on invoke; the Keld bound must be published as ▲ with its number. This is also the performance lever: pipelined invokes overlap kipc round trips instead of serializing 186 calls at ~50-100 us each.

**Evidence:**
- [fact] docs/specs/kel142-macos-renderer-bridge-api.md §4.1: 'Exactly one renderer-originated invoke may be pending per WebView in this minimum slice. ### X05-A4 — What is the hot-path cost model for the chatty one-way patterns (webContents.send main->renderer; ipcRenderer.send renderer->main; window event fan-out), and which rules keep facade hot paths allocation-free and semantically honest?

**Proposed answer:** Model (per call): Electron webContents.send = structured clone + one Mojo hop, in-process on the main side, synchronous throw at the call site for Function/Promise/Symbol/WeakMap/WeakSet arguments. Keld webContents.send = facade serialization in Bun -> one kipc frame Bun->host (today: TS FrameReader/WriteQueue allocate per frame; Rust read_frame allocates one Vec per payload) -> host routes to the window-bound virtual channel -> engine postMessage/evaluateJavaScript into the isolated world -> page listener. So Keld adds one extra process hop versus Electron's main process but removes Electron's main-process Chromium stack; whether net latency is better is UNMEASURED. Rules: (1) serialization semantics are the contract: throw synchronously at the facade for the same type set Electron rejects; do not silently drop or JSON-null them; (2) one serialization, one frame, no second buffering layer in the facade (the kipc WriteQueue is the only queue; arch 02 §6 'per-link single-producer queues'); (3) event fan-out from host to many windows is host-side routing, never N facade CALLs; (4) the zero-steady-state-allocation rule is arch 02 §6's destination and is NOT met by the live code (research 101/163) - the facade MUST NOT be claimed allocation-free until the attributed allocation lane in keld-benches shows zero per CALL in both Bun and Rust arms; until then the honest status is 'bounded, per-frame allocating'; (5) payload bound: MAX_FRAME_LEN 16 MiB for frames, MAX_PORT_MESSAGE_LEN 4096 for virtual ports - a webContents.send of a large object over a 4096-byte port path must fail with a typed error, not fragment silently.

**Evidence:**
- [fact] web-contents.md v44.4.5: contents.send 'Sending Functions, Promises, Symbols, WeakMaps, or WeakSets will throw an exception'; arguments serialized with the Structured Clone Algorithm (retrieved 2026-10-06)
- [fact] packages/@keld/kipc/src/transport.ts: FrameReader.push copies each chunk (`this.#chunks.push(new Uint8Array(chunk))`, line 432) and #copyOut allocates per payload (line 473, 591); writeFrame allocates header+payload (line 831)
