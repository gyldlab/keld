# F07 — renderer-webview-tag

_Research unit of the Electron compatibility wayfinder map; generated 2026-10-06; labels [fact]/[inference]/[unknown] as written by the unit agent; two independent refuters (invariants, Electron semantics) reviewed every decision._

## Summary

[fact] Family = Electron `webviewTag` element: 113 members (65 methods, 35 events, 13 attributes), renderer-only, not exported, carrying Electron's own "we recommend not to use the webview tag" warning. [fact] Corpus demand for the tag itself is zero: draw.io's 7 "webview" hits are six `webviewTag: false` and one `will-attach-webview` → `event.preventDefault()`; Zettlr and electron-quick-start contain no `<webview>`. What the corpus actually needs from this unit is the renderer-side compat user-script: `contextBridge.exposeInMainWorld` (draw.io 2, Zettlr 5), `ipcRenderer.send/on/once/removeListener/removeAllListeners` (draw.io), `ipcRenderer.invoke` (Zettlr 187 sites) and `sendSync` (Zettlr 6, synchronous `config.get` inside preload-exposed functions), `ipcRenderer.setMaxListeners(100)`, `process.type/versions/platform/env/argv` re-exposed to the page, `webPreferences.additionalArguments` read as `process.argv` in preload, `webUtils.getPathForFile`, and an isolated-world `window.navigation` listener that only works because page code cannot reach preload objects. [fact] Keld live state: macOS-only `window.keld.invoke` installed as a `WKContentWorld.defaultClientWorld` document-start user script plus a frozen pageWorld facade (channel 1 only, 4096 B, one pending invoke, host-minted document nonce, `KELD-WV-011`); WebView2 injects no bridge at all (wry's 96–109 ms blocking injection was deliberately removed); WebKitGTK is wry scaffold with no isolated world; no preload loading, no `@keld/web` package, no renderer `@keld/electron` shim, no custom scheme, no window registry beyond `LifecycleSession` window counting; devtools: WebView2 debug-on/release-off until guard owns `web.devtools`, wry open/close elsewhere. Recommended sequencing: (1) Tier-1 renderer user-script over `window.keld` (requires lifting the KEL-142 floor: multiple pending invokes, string channels, structured-clone codec, host→renderer events) with isolation claimed only on WebKit engines and a documented ▲ page-world emulation on WebView2; (2) `webviewTag:false`/`will-attach-webview` zero-webview semantics as a conformance cell now; (3) `<webview>` → host-owned child webview stays Tier 3 and is not on the draw.io/Zettlr path. Two design atoms need prototypes before any spec: `sendSync` feasibility on system engines (no synchronous native bridge exists on any of the three; only a synchronous XHR to a host scheme could block), and whether WebView2's page-world emulation of `contextBridge` leaks preload internals.

## Reuse points

- MacRendererBridge::install (crates/keld-wv/src/wkwebview/macos_bridge.rs): the only sanctioned isolated-world injection seam on macOS — preload + compat user-script must be appended to the same WKUserContentController in defaultClientWorld, never a second controller or a page-world script carrying authority.
- keld.wv-link/v1 decoder (crates/keld-wv/src/wv_link.rs, KELD-WV-011 reasons): extend its envelope kinds (e.g. event subscription, string-channel invoke) in place; do not add a second renderer control grammar.
- Host-minted document nonce bound to (WebviewId, navigation generation) (kel142 §5.2) = the Electron `event.senderFrame`/`sender` identity source; ipcMain sender validation maps onto it, never onto a caller-supplied field.
- @keld/kipc transport.ts (FrameReader, WriteQueue, RECEIVE_POLICIES, withIoDeadline) and @keld/api channels.ts AppChannel descriptor: ipcRenderer.invoke/ipcMain.handle must be AppChannel descriptors dispatched through dispatchApplicationCall, not a parallel reader.
- keld_runtime::virtual_port (VirtualPortRegistry, MAX_PORT_MESSAGE_LEN 4096, DEFAULT_PORT_QUEUE_CAPACITY 64, one-shot transfer): the owner for ipcRenderer.postMessage/MessagePort and for <webview>.send/sendToHost routing between embedder and guest principals.
- keld_guard::Principal::Webview + evaluate (default-deny, non-AppProcess denied before grant lookup, KELD-GUARD006/007): every renderer-originated channel/eval/devtools/print request is evaluated as the webview principal; remote-content webviews get channels: [] by default (arch 03 §4.3).
- WebView2 create ordering typestate (GuardInstalled proof before navigate_initial) in crates/keld-wv/src/webview2/mod.rs: add an 'InjectionComplete' witness from the AddScriptToExecuteOnDocumentCreated completion handler to the same chain (closes the #5716 race).
- keld_core::LifecycleSession window_opened/window_closed: child webviews must not count as windows (LastWindowClosed semantics) — reuse the counter, add a view kind, do not fork.
- KEL-135 profile identity (WKWebsiteDataStore identifier / WebView2 user-data folder / DACL): the only legitimate target for the <webview> `partition` attribute and `session` webPreference; `persist:` → identity-bound store, otherwise memory-only nonpersistent store.
- keld-pack ExpectedAppIdentity / verified manifest: preload bytes must be resolved from the verified app bundle by the host, never from an app-supplied absolute path; Electron's `file:`-only preload rule becomes 'bundle-relative, host-loaded'.
- KEL-98 echo codegen (checked-in TS payload declarations from Rust structs): the structured-clone value (SCV) codec for ipcRenderer args must be declared once and generated, not hand-mirrored in TS and Rust.
- keld-compat evidence schema (KEL-74) + crates/keld-compat/fixtures/lifecycle-corpus: zero-webview semantics (webviewTag:false, will-attach-webview never fires) and preload-order cells are added to the existing corpus, not a new harness.
- keld.compat.ts quirks flags / compat-scoreboard ▲ rule (crates/keld-compat/AGENTS.md): WebView2 page-world contextBridge emulation, missing process.versions.chrome, sendSync policy are declared divergences, chosen per PR.
- arch 02 §3 wv-link bulk lane (keld://c/{channel} via WKURLSchemeHandler / WebResourceRequested / WebKitGTK 2.40+ streams): the only sanctioned path for >4 KiB ipcRenderer payloads and for a synchronous-XHR sendSync experiment; depends on KEL-79.

### F07-A4 — Can ipcRenderer.sendSync keep its blocking caller contract on system engines, and through which lane?

**Proposed answer:** [fact] None of WKScriptMessageHandler (async reply), WebView2 postMessage (one-way JSON), or WebKitGTK message handlers block the calling JS. The only engine-neutral primitive that blocks the main thread with a reply is a synchronous XMLHttpRequest to a host-owned scheme/origin (the arch 02 §3 bulk lane). Proposed: sendSync = synchronous XHR POST to `keld://c/el-sync/{channel}` carrying the host-minted document nonce header, host enforces deadline + rate limit, dev build logs a warning per call (KEL-127 wording); response body is the SCV-encoded returnValue. Promise-returning emulation is rejected (changes caller contract; Zettlr's exposed `config.get` must return synchronously). If the prototype shows sync XHR is blocked by CSP/COEP or by engine policy on custom schemes, sendSync becomes a documented ✘ with per-call diagnostics.

**Evidence:**
- ipc-renderer.md: 'block the whole renderer process until the reply is received'
- research 06 bridge table: no binary/sync path; custom scheme streaming on all three (GTK 2.40+)
- arch 02 §3: bulk rides keld://c/{channel}; postMessage control-only
- briefing KEL-127: sendSync replacement must stay blocking CALL with deadline, rate-limited, dev-warned
- Zettlr preload: sendSync inside synchronous exposed functions (config.get/set, citation)

**Rejected alternatives:** Atomics.wait on SharedArrayBuffer (main thread cannot block on Atomics.wait in browsers; requires COOP/COEP and a worker relay). Busy-wait on a flag set by an async reply (freezes the event loop that must deliver the reply — deadlock). Async Promise shim with a quirks flag (violates KEL-127; breaks Zettlr synchronously).

**Confidence:** medium · **Type:** prototype · **Unknowns:** [unknown] Whether WKURLSchemeHandler serves synchronous XHR on the main thread without deadlock when the handler's reply is produced on the host UI thread (WKURLSchemeHandler callbacks arrive on the main thread; a round trip to Bun must not block that thread — KEL-142 §6 rule). ## Never list

- <webview nodeintegration> / webPreferences.nodeIntegration:true / nodeIntegrationInWorker / nodeintegrationinsubframes: Renderer Node integration is the briefing never-list item; Electron itself documents it disables the sandbox (sandbox.md) and escalates XSS to RCE (security.md item 2). Keld webviews have no ambient OS authority by construction.
- disablewebsecurity / webSecurity:false / allowRunningInsecureContent: Disables same-origin policy (security.md item 6, 8); Keld's webview principal/origin model (arch 03 §1) and CSP injection depend on SOP.
- enableblinkfeatures / disableblinkfeatures / experimentalFeatures / webpreferences feature strings beyond the allowlisted subset: Arbitrary Chromium/Blink flags are on the briefing never-list; they are meaningless on WebKit engines and would make behavior engine-divergent and unmeasurable.
- plugins attribute: Browser plugins (PPAPI) have no equivalent on any system engine and widen attack surface; documented-never.
- inspectServiceWorker / inspectSharedWorker / any CDP-backed webview method in production: Full Chrome DevTools Protocol in production webviews is on the never list (briefing; research 13); only WebView2 even has CDP.
- sendInputEvent from a renderer (embedder) into a guest: Synthetic OS-level input injection is authority a webview principal must not hold; at most legacy-profile with explicit grant, never default.
- Exposing raw ipcRenderer / ipcRenderer.on / Node globals via contextBridge in Keld-authored shims: Electron's own guidance (context-bridge.md 'security footgun'; security.md item 20); Keld's shim exposes only the typed facade, and corpus apps that do this get their own code's behavior, not a Keld-provided escape hatch.
- A second renderer-native handler (`window.ipc`, `window.electron` native object) beside window.keld: KEL-142 Independence and §12 forbid a second renderer-routing protocol; one wv-link decoder, one document nonce, one app-link.
- process.env passthrough of the real host environment to preload/page: Zettlr copies process.env into the page; on Keld the host environment is authority-bearing material (app-link tokens live in the host) — only a declared allowlist is exposed.
- enableWebSQL / WebSQL: Removed from modern WebKit and Chromium; cannot be polyfilled honestly; documented-✘.

- [medium] process.env re-exposure to the page (Zettlr: `env: Object.assign({}, process.env)`) is an information-flow decision with no owner: on Keld the renderer has no process, so the shim must synthesize env. Copying host env into an untrusted webview principal leaks host environment (paths, tokens) across the trust boundary in arch 03 §1. Must be declared: empty object or a manifest-declared allowlist, scored ▲. — docs/architecture/03-security.md §1 principal table (webview untrusted); corpus/zettlr preload line 91.
- [high] Synchronous cross-world calls are a missing design atom. Zettlr exposes functions whose page-visible return value is produced synchronously (config.get, getCitationCallback → sendSync). Even if sendSync itself is solved via a synchronous XHR to a host scheme, the isolated→page function proxy must also be synchronous. The existing KEL-142 relay is async window.postMessage.
