# F09 — update-packaging

_Research unit of the Electron compatibility wayfinder map; generated 2026-10-06; labels [fact]/[inference]/[unknown] as written by the unit agent; two independent refuters (invariants, Electron semantics) reviewed every decision._

## Summary

Electron's autoUpdater is a 10-member module (setFeedURL/getFeedURL/checkForUpdates/quitAndInstall + 6 events), macOS+Windows only, that delegates verification and installation to Squirrel.Mac / Squirrel.Windows / MSIX and takes an app-selected feed URL [fact: v44.4.5 auto-updater.md]. Neither corpus app uses it directly: draw.io uses electron-updater v6 (setFeedURL({provider:'github',...}), autoDownload=false, autoInstallOnAppQuit, downloadUpdate, download-progress, info.version, logger) and Zettlr ships its own got-based downloader (shell.openPath of the downloaded installer + app.quit) [fact: corpus grep]. Keld today: keld-update implements signed v0 manifest/full verification, Windows x64 extraction/staging, PerUserDirect journaled activation, read-only active selection and startup repair; keld-pack streams Windows v0 packages only; keld-cli `build`/`migrate` are reserved (KELD-CLI-045); @keld/electron exports only `app`; no update event channel to Bun, no keld.build.ts schema, no autoUpdater facade, no bridge recipe [fact: product-status.tsv rows 9/10/13, crates, packages]. Feed orchestration, candidate launch, 30-second health, host consumer, macOS/Linux package cells (blocked on KEL-137 + KEL-103) are TARGET. Design answer: implement ONE host-owned updater (KEL-53) and expose two thin Bun facades over kipc — Electron-core `autoUpdater` and an electron-updater-shaped shim for migrated apps — with the feed URL compiled into the signed host (never app-selected), staged≠activated semantics documented as ▲, errors mapped from KELD-UPDATE-*; `keld migrate` translates electron-builder/forge config into keld.build.ts with a per-field disposition report (fuses/ASAR/custom hooks → explained drops); the arch 04 §7 bridge release is constrained by electron-updater's publisherName Authenticode check + NSIS spawn args on Windows and by Squirrel.Mac's designated-requirement check on macOS, and is only reachable for Windows x64 until KEL-137/KEL-103 land. Six decision atoms below; three prototypes; evidence receipts attached.

## Reuse points

- keld-update UpdateVerifier → AdmittedInstallation::verify_manifest → SelectedFull → verify_full → Windows extraction → PerUserDirect journaled transaction: the ONLY updater state machine; the facade adds no verification, selection, download or activation logic.
- keld-pack ExpectedAppIdentityPayload (key, app id, channel, target) as the compiled-in feed identity that setFeedURL is checked against and getFeedURL reports.
- KELD-UPDATE-001..018 typed errors with Display guidance → Error.message/Error.code for the `error` event; no remapping (KEL-53 §4: 'CLI/compat render them without remapping').
- keld-update Channel {Stable, Beta, Canary} as the only legal keld.build.ts channel values (draw.io's per-arch 'latest-arm64' channel maps to Keld's per-target feed path instead).
- @keld/api app lifecycle (quit(): Promise<void>, onLastWindowClosed) and @keld/electron app facade pattern (per-listener try/catch isolation, KEL-72 ▲ conventions) for autoUpdater's EventEmitter shape and the quitAndInstall sequence.
- KEL-98 echo-codegen contract source for the update.check/update.download/update.quitAndInstall calls and the event stream (no new IDL; KEL-127).
- keld-guard manifest grants (keld.permissions.jsonc) for the three update calls; KEL-102 host enforcement; KEL-80 virtual channels/backpressure for progress events.
- KEL-74 evidence schema + KEL-237 lifecycle corpus for the F09 conformance cells and the L3 'electron-updater shim' denominator row; crates/keld-compat/AGENTS.md ordering-test rule.
- arch 06 §4a static feed tree (CDN/S3/GitHub Releases, no server logic) — the bridge publishes Keld's updates.json(.sig) and electron-updater's latest*.yml in the same GitHub Release assets.
- keld-pack formats and native signers (rcodesign / signtool / osslsigncode) as the targets keld.build.ts signing config drives; KEL-19 payload writer embeds identity before final Authenticode signature.
- KEL-254 ActivePackageSelection / startup LKG republish for the 'app relaunched into old version after failed health' observable (app.getVersion()).
- KEL-75 named roles with no inherited env/cwd/argv as the Keld invariant that subsumes RunAsNode/NodeOptions/NodeCliInspect fuses; KEL-79 webview origin policy for GrantFileProtocolExtraPrivileges; KEL-135 profile identity for CookieEncryption parity question; KEL-215 addon qualification for asar.unpack '*.node'.

## Decisions (with refuter verdicts)

### F09-A1 — Which updater contract does the compat layer clone: Electron-core `autoUpdater` (the F09 census) or the electron-updater v6 surface the corpus actually calls?

**Proposed answer:** Both, as two thin Bun facades over ONE host-owned KEL-53 state machine: (a) `@keld/electron`.autoUpdater implements the 10-member Electron-core surface for the per-API scoreboard; (b) `keld migrate` rewrites `electron-updater` imports to a Keld-owned shim exporting the AppUpdater subset draw.io exercises (autoDownload, autoInstallOnAppQuit, downloadUpdate, download-progress, update-available(info.version), update-downloaded, error(err), logger, checkForUpdates():Promise<result|null>, quitAndInstall(isSilent?, isForceRunAfter?)). Provider options ({provider:'github', owner, repo, channel}) are parsed only to cross-check against keld.build.ts and never contacted. Zettlr needs neither (custom got downloader) and scores N/A in this family. Declared as an L3 ecosystem row in the KEL-74 denominator, not as Electron API.

## Never list

- autoUpdater.setFeedURL / electron-updater provider options / requestHeaders / headers / serverType / login as feed authority: App-selected feed URLs into a privileged updater are on the program never-list; Keld's key/app id/channel/target are compiled into the signed host (arch 06 §4a step 1; research 186 row 10).
- allowDowngrade / channel-switch downgrade / allowAnyVersion: KEL-53's monotonic protected floor is the replay/downgrade defense; honoring downgrade flags would reopen it.
- App-executed installers or exposure of staged artifact paths (electron-updater downloadedFile/updateFile, NsisUpdater spawn, Zettlr shell.openPath of an installer): KEL-53 forbids arbitrary relaunch helpers and role-writable update state; raw spawn from strict roles is never-listed.
- app.relaunch({execPath}) to an updater/Squirrel layout: Candidate launch is host-owned under the exact initiating token; app-chosen exec paths are a privilege path.
- Electron's MSIX self-update path and any direct mutation of store/package-manager installs: ManagedOwner mode refuses direct activation and registers no competing writer (arch 06, KEL-53 non-goals).
- @electron/fuses as a runtime or permission API: Fuses are Electron-binary hardening bits; Keld's equivalents are host invariants, not app-toggled flags (research 186 row 8).
- ASAR virtual filesystem / original-fs / app.asar.unpacked path contracts: Keld ships a signed canonical plain tree; an fs shim per role would duplicate FsBroker policy.
- Executing electron-builder/forge JS hooks (afterPack/afterSign/custom sign scripts) inside keld build: Arbitrary project code inside the trusted packaging/signing step and a plugin surface Keld does not offer; declarative signing config only.
- Running Electron's api-autoupdater-*-spec.ts under Bun as the oracle: Research 214 refuses running Electron's spec tree; cite test identities via an approved per-surface spec and land Keld-owned tests.
