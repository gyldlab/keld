Keld window lifecycle: can a host-owned window model reproduce Electron's?

Logic prototype for the Electron compatibility map (units F01 app lifecycle, F02 windowing, F03 webContents). It is a model you can drive, not product code and not OS evidence.

The question. When the Rust host owns every native window and the Electron-shaped objects live in a supervised Bun role, does the app still observe Electron's BrowserWindow lifecycle (ready-to-show, show, close with preventDefault(), closed, destroy(), isDestroyed(), the window-all-closed default quit, and app.quit(): before-quit, then per-window close, then will-quit, then quit) while the Bun role can crash and be replaced without the window disappearing?

Every button below calls one pure state machine. The panel on the right is the whole state; the transcript shows each Electron-observable event, each kipc message and each native effect in order. Illegal moves return the error the real system would return, with its fix text. Labels on the last section say which semantics are Electron facts, which are decided Keld design, and which are still open.
