Keld host-mediated IPC: does it reproduce Electron ipcMain / ipcRenderer semantics?

Bounded question (unit F04, map gyldlab/keld#391). A Keld renderer never talks to the Bun main role directly: every message is renderer → Rust host → Bun role over one kipc link. This page is a logic model of that path. It asks whether the decided design reproduces the Electron v44.4.5 behaviours an unmodified app depends on:

  • ipcRenderer.invoke / ipcMain.handle round trip
  • handler throw → message-only error in the renderer; typed KELD-* code stays on the wire
  • send / on ordering per channel
  • sendSync as a blocking CALL with deadline + rate limit + dev warning, scaffolded (typed throw + fix-it) until the transport experiment passes
  • webContents.send targets the current main frame of one webview principal
  • event.reply bound to the sender document generation; stale replies dropped silently
  • event.senderFrame may be null
  • bounded credit window: a slow consumer produces a typed error, never an unbounded queue
  • ungranted el:<channel> refused with KELD-GUARD003; el:* refused by keld migrate
  • the renderer never obtains a Bun endpoint
  • a parked Bun main thread that owns the socket stalls the link after 8 KiB; a worker-owned single link does not

Planning artefact only. Nothing here is Keld product code and no implementation is authorised by it. The reducer in the first <script> block has no DOM access and is the part meant to be lifted (as a conformance-fixture oracle or a design reference). Every semantic is labelled FACT INFERENCE or PROPOSED in the last section; anything still open on the map is PROPOSED.
