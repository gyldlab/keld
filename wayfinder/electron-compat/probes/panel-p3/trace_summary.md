## 6. The exact Bun error without the harness, and the fix

Command: `cd drawio-desktop && HOME=<fakehome> bun --no-install src/main/electron.js` (no preload). Verbatim stderr, captured by `harness/run-all.sh` into `harness/baseline-error.txt`:

```
SyntaxError: Export named 'BrowserWindow' not found in module '/private/tmp/claude-501/-Users-centillionaire-WORK-keld/9d46ef65-830a-4067-90bc-f68a26ad7f85/scratchpad/p3/drawio-desktop/node_modules/.bun/electron@44.5.1/node_modules/electron/index.js'.

Bun v1.4.2 (macOS arm64)
```

Cause: under a plain runtime the npm `electron` package is only a CJS module whose `module.exports` is the path of the Electron binary; the real `electron` API exists only inside the Electron process. The first static `import {..., BrowserWindow} from 'electron'` (src/main/electron.js line 5) fails at link time, before any app code runs.

Fixes tried on the way to a working harness (all Bun 1.4.2):

1. `Bun.plugin` `onResolve({filter:/^electron$/})`: never invoked for the static bare-specifier imports (it fired only for the entry file), so `electron` stayed unresolved. Dead end.
2. `build.module("electron", () => ({exports, loader:"object"}))` in a `--preload`ed plugin: works for ESM named/default imports and for CJS `require("electron")` from dependencies. **This is the fix that is used.**
3. `build.module("fs"|"child_process"...)` to wrap builtins: rejected by Bun (`module() cannot be used to override builtin module "fs"`).
4. Patching the builtin objects after an ESM `import fs from "node:fs"` in the preload: ESM *named* bindings (`import {spawn} from "child_process"`) stayed unpatched. Fix: preload is CommonJS and patches via `require()` before any ESM import of the builtin; then named, default, namespace and `fs/promises` imports all see the wrappers (proved by the canary, section 7).
5. `onLoad` source rewriting to redirect builtin specifiers: abandoned, because returning `{contents, loader:"js"}` for a CommonJS file makes Bun treat it as ESM (`module.exports` lost, `import x from "./c.cjs"` has no default).
6. `bun --no-install` is mandatory. In a scratch dir with no `node_modules` above it, Bun auto-installs missing bare imports from the npm registry **and runs the package's installer** (it fetched `electron@44.6.0` and started the Electron binary download into `HOME/.bun/install/cache`). See "Disclosure" below.

## 9. Findings worth carrying forward (numbers are from the 2026-10-07 run in this directory)

**What the run proves.** The unmodified `src/main/electron.js` plus the 63 npm packages it pulls in at runtime evaluate and run on Bun 1.4.2 against a recording fake `electron`. All five phases complete in both variants, there are no unresolved Electron members, no uncaught exceptions or unhandled rejections, and no failed steps. `child_process` is silent in every phase (see surprise 2).

**Surprises, most important first.**

1. **The trace you get depends on `app.isPackaged`.** With `isPackaged=false` (the raw dev tree) electron-updater logs "Skip checkForUpdates because application is not packed" and does nothing: no network, no `.updaterId`, no log file, no dialog. With `isPackaged=true` (what ships) the boot adds: read+write of `userData/.updaterId` (a persistent per-install id), `electron.net.request` GET `https://github.com/jgraph/drawio-desktop/releases.atom` carrying header `x-user-staging-id`, a `session.fromPartition`, and, because the request is refused, an "Update Error" `dialog.showMessageBox` plus four writes to `Library/Logs/draw.io/main.log`. The difference between the variants is 9 fs events, 1 network attempt, 1 dialog, a `session.fromPartition`, and a few extra `app`/`os` reads. The primary `trace.jsonl` therefore uses `isPackaged=true`; `trace.unpackaged.jsonl` is the literal dev tree.
2. **Zero `child_process` events, and the harness can see them.** The canary proves named `import {spawn, execFile} from 'child_process'` is intercepted. The app's only spawn sites are Windows-only (`attrib.exe`) and the renderer-triggered `getLocalFonts` (`execFile fc-list`), which this open/save/close scenario never calls.
3. **`electron-store` is a disk round-trip per call.** 32 `readFileSync` of `config.json` over the run (17 in boot alone) and 9 full atomic rewrites (tmp file, `fsync`, `chown`, `rename`). Rewrites come from first-run migrations (4), every dialog-blessed path (3: `persistBlessedPaths` writes the whole set, including paths that do not exist yet), and every window `close` event (2: `rememberWinSize`). The persisted `blessedPaths` array in `config.json` is the durable record of what the user authorised.
4. **The app's own default-deny gate works, and it consults the renderer.** All 6 negative probes were refused with `path not authorised`: unblessed read, `../` traversal, read inside the app bundle, unblessed write, write into `userData`, write outside `p3`. On the first denied read main calls `webContents.executeJavaScript` with a 2,154-character script to collect the renderer's configured library/template paths before refusing; the result is cached for later denials.
5. **Dependencies register IPC channels, and the preload bridge can reach any of them.** `electron-log` registers `__ELECTRON_LOG__` (on and handle) and `electron-store` registers `electron-store-get-data` at import, before `ready`. `src/main/electron-preload.js` exposes `sendMessage(action, args)` as a raw `ipcRenderer.send(action, args)` with a renderer-chosen channel name. From source reading (not from the trace): the app's handlers call `validateSender`, but electron-store's handler (`electron-store/index.js:25`) does not. Any Keld channel allow-list must therefore be generated from the full registered set above, not from `src/main` alone.
6. **Update-failure UI is deduplicated.** Three error signals fire for the one refused request (the `net` error, the `autoUpdater` `error` event, and the `checkForUpdates` rejection) but only one `dialog.showMessageBox` call appears, because of `updateFailureDialogShown`.
7. **`app.on('open-file')` is registered only after `will-finish-launching`**, i.e. during boot, not import. A harness that emits `ready` without `will-finish-launching` would silently lose file-association opens.
8. **On macOS closing the last window does not quit.** `window-all-closed` is emitted; the handler only calls `app.quit()` when `cmdQPressed` or not macOS, so `app.quit` is correctly absent from the trace.

**Bun-specific findings.**

- Static imports of a bare specifier are not routed through `Bun.plugin` `onResolve`; `build.module()` is the working hook (section 6).
- ESM named imports of Node builtins are snapshots taken when the builtin's ESM facade is first built. Patching the CJS object from a CommonJS preload (`require`, not `import`) before any ESM import is what makes named/default/namespace imports all observe the wrappers.
- `child_process` in Bun is layered on `Bun.spawn` and copies the whole `process.env` through any Proxy installed on it (65 `env.get` events per spawn before muting). A Proxy-based env policy in a Bun-hosted runtime sees this internal traffic and has to distinguish it from app reads.
- `os.tmpdir` is a lazy accessor, not a data property; a wrapper that only looks at `descriptor.value` silently misses it.
- `process.env = new Proxy(...)`, `process.versions.electron = ...`, `process.type = ...` and instance-level patching of `fs.promises` `FileHandle` methods all work in 1.4.2.
- `import {X} from 'electron'` with a missing name is a link-time `SyntaxError`, not `undefined`, so the fake must export every name the app imports (it exports all 43 main-process names from `electron.d.ts`).

**Harness decisions and known deviations (read before trusting a negative).**

- Stubs are plausible, not verified against a real Electron 44 binary. `will-finish-launching` is emitted **before** `ready` (real order); the task text listed them the other way round.
- Primary run: `app.isPackaged=true`, `process.defaultApp=true`, `process.argv=[<Electron>, '.']` (so no CLI file arguments), `process.type='browser'`, `process.versions.electron='44.5.1'`.
- The "renderer" is a script that calls the same `rendererReq` actions in the order read from `ElectronApp.js` (open: `getDocumentsFolder`, `showOpenDialog`, `dirname`, `readFile`, `fileStat`, `isFileWritable`, `getFileDrafts`, `watchFile`; save: `saveDraft`, `saveFile`, `deleteFile`, Save As, export `writeFile`). A real renderer may interleave or repeat them differently.
- Dialogs resolve immediately from queues. The close scenario answers Cancel then Discard; the Save branch of the three-button dialog (`saveAndClose` round trip) and a second window via `newfile` were not driven.
- Network is refused, not simulated: the updater's failure path (log writes, error dialog) is the offline behaviour, not necessarily the online one.
- `caller` is the first `src/main` frame on the JS stack. Async continuations lose frames, so events from `await`ed library code carry `caller:null` and a `via` package frame instead; about 46 of the 441 authority events in the primary trace have no `src/main` frame.
- Harness write guard: any fs write whose path resolves outside `p3/` is refused and recorded (`blocked:"outside-sandbox"`). It fired only for the canary; the app never attempted one.
- Timers that outlive the run (the 5 s `fs.watchFile` poll, updater retries) are cut off by `process.exit`; nothing was observed after the final `fs.unwatchFile`.

**Not exercised** (no events means not driven, not safe): CLI export mode (`-x`) and the `export` IPC (hidden window, pdf-lib, file output), `second-instance` and `open-file` launches, `getLocalFonts`, `openExternal`, `clipboardAction`, `windowAction`, `exit`, `checkFileExists`, `getBkpFile`, Windows and Linux branches, a real renderer (CSP header injection, `contextBridge`, `webSecurity`), and update download/install.

## 10. Disclosure and reproduction

- **Stray network access during harness development.** An early scratch test ran Bun in a directory with no `node_modules` above it and without `--no-install`. Bun auto-installed `electron@44.6.0` and its dependencies from the npm registry and started the Electron binary download into `p3/fakehome/.bun` and `p3/fakehome/Library/Caches/electron` (323 MB). Nothing outside `p3/` was written; the directories were deleted immediately and every harness run since uses `bun --no-install`. The application under test never had network access.
- `p3/static_inventory.tsv` was not created by this harness; it appeared during the session and was left untouched.
- Reproduce: `harness/run-all.sh` (runs the unpackaged variant, then the packaged-like primary, then `bun --no-install harness/summarize.mjs`). Single run: `harness/run.sh [packaged|unpackaged]`. Everything is written under `p3/`; `fakehome/` and `fixtures/` are rebuilt on each run.
